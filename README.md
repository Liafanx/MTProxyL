# MTProxyL

**MTProxyL** — менеджер Telegram MTProto прокси на базе движка **[telemt](https://github.com/telemt/telemt)** (Rust).

А также реанимация уже существующего прокси.

Установка в один клик. Полный контроль.

<a id="install"></a>

## Установка

```bash
wget -qO /tmp/mtproxyl-install.sh https://raw.githubusercontent.com/Liafanx/MTProxyL/main/install.sh && sudo bash /tmp/mtproxyl-install.sh && source ~/.bashrc
```

После установки запускается мастер настройки.
Для повторного входа в меню:

```bash
mtproxyl
```

> **На сервере с 1 ГБ памяти и без подкачки** установка предложит создать файл
> подкачки на 1 ГБ (по умолчанию да). Без него docker, движок и особенно сборка
> панели упираются в нехватку памяти: ядро убивает процесс, а установка выглядит
> зависшей. Управлять отдельно: `mtproxyl swap status|on|off`.

> MTProxyL работает от root. Если вы заходите на сервер обычным пользователем,
> установщик заводит алиас `mtproxyl` → `sudo mtproxyl` (в `/etc/profile.d/` и
> в вашем `~/.bashrc`), поэтому `sudo` дописывать не нужно. `source ~/.bashrc`
> в команде выше применяет алиас сразу, без перезахода. Под root алиас не
> определяется — команда и так работает напрямую.

> При первой установке скрипт первым предлагает **Zapret2 MTProto fix** (по умолчанию Y) — серверный обход через TCP-манипуляции. Если отказаться — предлагается **NFT Smart By-MEKO** — рекомендуемый режим с разделением iOS/Android.

<a id="quickstart"></a>

## Быстрый старт

1. Запустите установку:
   ```bash
   wget -qO /tmp/mtproxyl-install.sh https://raw.githubusercontent.com/Liafanx/MTProxyL/main/install.sh && sudo bash /tmp/mtproxyl-install.sh && source ~/.bashrc
   ```

2. Следуйте мастеру настройки — выберите порт, домен, IP, режим обхода

3. Получите ссылку на прокси (выводится после установки) или:
   ```bash
   mtproxyl secret link
   ```

4. Откройте ссылку в Telegram — готово!

> Один порт для **всех** клиентов (iOS, Android, Desktop) — никаких дополнительных настроек.

<a id="install-args"></a>

## Установка аргументами, без вопросов

Мастер установки удобен один раз. Когда адрес прокси заблокировали и надо
срочно подняться на другой машине, вопросы только мешают: параметры уже
известны, их нужно повторить в точности. С версии 1.5.2 всю установку
менеджера можно задать аргументами — ни одного вопроса не будет.

```bash
wget -qO /tmp/mtproxyl-install.sh https://raw.githubusercontent.com/Liafanx/MTProxyL/main/install.sh
sudo bash /tmp/mtproxyl-install.sh -- \
  --mode manager --port 443 --host proxy.example.com --sni m.beboo.ru \
  --secret vpn:0123456789abcdef0123456789abcdef \
  --ad-tag 89abcdef0123456789abcdef01234567 \
  --zapret2 yes --selfmask proxy.example.com --selfmask-cert letsencrypt
```

Всё, что стоит после `--`, уходит команде `mtproxyl install`. На уже
установленной машине её можно звать и напрямую:

```bash
mtproxyl install --mode manager --port 443 --secret vpn:0123…ef --force
mtproxyl install --help          # полный список аргументов
```

| Аргумент | Что задаёт |
|---|---|
| `--mode manager` | режим; аргументами ставится только менеджер |
| `--port N` | порт прокси, по умолчанию 443 |
| `--metrics-port N`, `--api-port N` | порты метрик и REST API движка; без них берётся первый свободный |
| `--host <ip\|домен>` | что подставлять в ссылки; без него — свой публичный адрес |
| `--sni <домен>` | FakeTLS домен, по умолчанию `autoscout24.ru` |
| `--secret [метка:]<32 hex>` | секрет; ключ можно повторять — сколько раз, столько пользователей |
| `--ad-tag <32 hex>` | рекламная метка |
| `--mask on\|off` | маскировка трафика |
| `--sni-policy mask\|drop\|accept\|reject_handshake` | что делать с чужим SNI |
| `--cpus N`, `--memory 512m` | лимиты контейнера; без них — без ограничений. `--cpus` не может превышать число ядер машины, иначе docker не запустит контейнер |
| `--zapret2 yes\|no` | Zapret2 MTProto fix, по умолчанию да |
| `--syn-limiter meko\|classic\|off` | SYN-лимитер, если Zapret2 не ставится |
| `--limiter-action icmp\|reject\|drop` | действие для не-iOS в режиме meko |
| `--meko yes\|no` | оптимизация системы By-MEKO |
| `--selfmask <домен>` | включить Selfmask на этом домене |
| `--selfmask-cert letsencrypt\|selfsigned` | тип сертификата |
| `--selfmask-email`, `--selfmask-template`, `--selfmask-backend-port` | остальные параметры Selfmask |
| `--force` | ставить поверх существующей установки |

> Реаниматор аргументами не ставится: там параметры берутся с самого сервера —
> у чужой цели свой конфиг, свой порт и свой движок, и задавать их со стороны
> нечем.

> Selfmask с Let's Encrypt требует A-записи домена **на этот сервер**. Если она
> ещё смотрит на старую машину, установка не станет выпускать сертификат, а
> скажет об этом: остальное поставится, Selfmask доделаете позже командой
> `mtproxyl selfmask setup`. С `--selfmask-cert selfsigned` A-запись не нужна.

<a id="migrate"></a>

## Переезд на другой сервер

Установка аргументами избавляет от вопросов, но параметры всё равно надо
собрать руками. `mtproxyl migrate` делает это сам: читает свои же настройки и
поднимает на новой машине копию — тот же порт, домен ссылок, FakeTLS SNI,
секреты с лимитами и квотами, рекламная метка, маскировка, SNI-политика,
Zapret2 или SYN-лимитер, оптимизация By-MEKO, Selfmask, веб-панель и
телеграм-бот. Меняется ровно одно — адрес сервера.

```bash
mtproxyl migrate root@203.0.113.10          # переезд целиком
mtproxyl migrate root@203.0.113.10:2222     # если SSH не на 22
mtproxyl migrate root@203.0.113.10 --dry-run  # показать, что поедет
```

Из меню: **Обновления и бэкапы → Переезд на другой сервер**.

> **Сначала A-запись, потом переезд.** Сертификат Let's Encrypt выпускается
> в момент установки: проверка домена идёт туда, куда сейчас смотрит A-запись.
> Пока она на старом сервере, на новом не поднимутся ни Selfmask, ни HTTPS
> панели — всё остальное переедет, но это придётся доделывать руками
> (`mtproxyl selfmask setup`, `mtproxyl panel cert <домен>`). MTProxyL сверяет
> записи до начала работ, называет, куда они ведут сейчас, и переспрашивает.
> С самоподписанным сертификатом (`--selfmask-cert selfsigned`) A-запись не
> нужна вовсе, и порядок неважен.

Как это работает:

1. Проверяется вход по SSH. **Только по ключу** — пароль MTProxyL не
   спрашивает и не хранит. Если ключа на той стороне нет, предлагается
   `ssh-copy-id`: пароль в нём вводите вы, и он никуда не попадает. Если ключ
   хоста изменился (обычное дело после переустановки системы на том же
   адресе), MTProxyL показывает новый отпечаток и забывает старый ключ только
   с вашего согласия — молча такое не чинят.
2. Новый сервер осматривается заранее: есть ли root, что за система, не занят
   ли нужный порт, не стоит ли там уже MTProxyL, какой у него адрес.
3. Спрашивается, переносить ли панель и бота — по умолчанию да.
4. Сверяются A-записи доменов с адресом новой машины и называется всё, что
   упрётся в непереведённую запись.
5. Показывается сводка «что поедет» и спрашивается подтверждение.
6. На новой машине скачивается установщик той же ветки и запускается с
   собранными аргументами — ставятся пакеты, docker, движок, фиксы, автозапуск.
   Затем проверяется, что контейнер действительно поднялся.
7. Довозится `secrets.conf` целиком: лимиты, квоты, сроки и заметки аргументами
   не передать.
8. Едет конфиг режима супер эксперта, если он включён, и режим включается на
   новой машине. Выключить его там можно в любой момент — файл не удаляется,
   а MTProxyL возвращается к своему конфигу из перенесённых настроек.
9. Панель переносится вместе с `config.toml` — логин, хеш пароля и `jwt_secret`
   остаются прежними, мастер настройки на новой машине не запускается. Если
   Selfmask на новой машине поднялся, панель получает его сертификат и остаётся
   на домене, а не на голом IP. Бот ставится с прежним токеном и списком
   админов; если с нового сервера не видно `api.telegram.org`, бот пропускается
   — там он всё равно не заработает. Ответить заранее можно флагами
   `--panel`/`--no-panel` и `--tgbot`/`--no-tgbot`.
10. В конце предлагается удалить копию на старом сервере — по умолчанию нет:
    сначала проверьте новую.

Чего переезд **не** делает:

- **Не переводит A-запись.** Домен ваш, DNS ваш — переключаете вы. Пока запись
  смотрит на старый адрес, ссылки ведут туда же, а Selfmask с Let's Encrypt на
  новой машине не выпустит сертификат.
- **Не переносит литеральный IP в ссылках.** Если в настройках ссылок стоял
  адрес, а не домен, на новой машине он определится заново — ссылки изменятся,
  и клиентам их придётся раздать заново. Домен переезжает как есть.
- **Не переносит лимиты CPU и памяти контейнера.** Их подбирали под старую
  машину: если на новой ядер меньше, docker откажется запускать контейнер
  («range of CPUs is from 0.01 to 1.00»). На новой машине они остаются
  свободными, задать их заново — «Настройки» в меню.
- **Не работает в режиме реаниматора.** Там цель чужая: её конфиг, движок и
  данные не наши, копировать нечего.
- **Не переносит настройки гео-блокировки** — их задайте на новой машине заново.

> Если MTProxyL стоит из ветки, а не из `main`, панель на новой машине будет
> **собираться из исходников** в Docker — это несколько минут и заметная
> нагрузка. На маленькой машине сборка может съесть всю память. Переезд об
> этом предупреждает перед вопросом про панель.

> Два прокси на одних секретах и один токен бота на двоих — источник странных
> симптомов. Старую копию стоит выключить сразу после проверки новой.

<a id="modes"></a>

## Режимы работы: Manager / Reanimator

С версии 1.3.0 MTProxyL умеет работать в двух режимах — выбор происходит на первом шаге мастера установки (`mtproxyl install`):

- **Manager** *(по умолчанию, прежнее поведение)* — MTProxyL сам устанавливает движок telemt (образ из GHCR или сборка из исходников), сам генерирует `config.toml`, управляет секретами/upstream'ами/бэкапами и своим Docker-контейнером.
- **Только оптимизация** — вырожденный случай реаниматора для тех, у кого прокси
  свой: другая реализация MTProto (например, teleproxy) или вообще другой
  сервис. MTProxyL тогда работает как набор host-фиксов — zapret2, SYN-лимитер,
  оптимизация By-MEKO, гео-блокировка, дополнения — и не спрашивает ни про
  конфиг, ни про домен, ни про порт движка. Пункты про пользователей, ссылки и
  статистику из меню уходят: брать их неоткуда. Предлагается при установке
  реаниматора, если telemt на сервере не нашёлся, и включается позже в
  «Цель / режим» → «Только оптимизация»; там же выключается обратно.
- **Reanimator** — вместо установки MTProxyL ищет уже работающую установку telemt на сервере (Docker-контейнер сторонней панели, MTProxyMax, голый процесс/systemd-юнит `telemt.service` или просто конфиг-файл) и применяет к ней тот же арсенал фиксов: NFT SYN limiter, Zapret2 MTProto fix, iOS-фиксы, оптимизацию By-MEKO и точечный тюнинг `config.toml` — не устанавливая ничего и не перезаписывая чужой конфиг целиком. **Если telemt на сервере нет вовсе — предложит поставить оригинальный из официального репозитория [`telemt/telemt`](https://github.com/telemt/telemt)** ([подробнее](#modes)).

Переключение режима в любой момент — при переходе учитывается состояние
установки: из Reanimator в Manager, если своего telemt ещё нет, сразу
предлагается мастер установки; из Manager в Reanimator предлагается
остановить/удалить свой контейнер, чтобы он не держал порт цели.

Несколько установок на одном сервере не запрещены (например, контейнер
менеджера на 8443 и системный telemt на 443) — при занятом порте мастер
показывает, кто его слушает, и позволяет либо выбрать другой порт, либо
продолжить осознанно.

```bash
mtproxyl mode                # текущий режим
mtproxyl mode reanimator      # перейти в Reanimator (с подтверждением)
mtproxyl mode manager         # перейти в Manager (с подтверждением)
mtproxyl detect               # повторно найти цель (Reanimator)
mtproxyl edit-config          # открыть конфиг цели в редакторе (Reanimator)
mtproxyl install-telemt       # поставить/обновить оригинальный telemt (Reanimator)
mtproxyl uninstall-telemt     # удалить telemt: uninstall или purge (Reanimator)
```

Если на сервере вообще нет telemt — ни процесса, ни службы, ни бинарника —
чинить нечего, и MTProxyL предлагает поставить **оригинальный** telemt:
запускается официальный установщик проекта
([`telemt/telemt`](https://github.com/telemt/telemt), `install.sh`) как есть,
со своими вопросами про язык, порт и TLS-домен. Предложение появляется при
установке в режиме Reanimator, отдельным пунктом в главном меню и в меню
«Цель / режим». После установки цель обнаруживается заново, порт
синхронизируется с её конфигом и предлагается тюнинг таймаутов. Перед запуском
можно выбрать версию telemt — список релизов показывается по 10 на страницу,
по умолчанию ставится latest. Тем же установщиком telemt можно удалить
(`uninstall` — служба и бинарник, `purge` — вместе с конфигом и пользователем).

Установщик управляет только `telemt.service`: если цель — Docker-контейнер
сторонней панели или MTProxyMax, он её не обновляет, а ставит рядом отдельную
службу. При обновлении конфиг цели не перезаписывается целиком: меняются только
порт и `tls_domain`, а тюнинг, `[server.api]` и секреты остаются на месте.

Порт проверяется до запуска установщика. Отдельно разбирается случай, когда
порт держит собственный контейнер MTProxyL: он работает в сети host, поэтому
установщик telemt видит в `ss` процесс с именем `telemt`, считает порт своим и
продолжает установку — служба после этого не может занять порт. MTProxyL
предложит остановить или удалить контейнер либо указать в установщике другой
порт.

### Что доступно в режиме Reanimator

Меню и CLI адаптируются под режим: пункты, требующие владения движком/конфигом,
скрываются, а остальные работают против **цели**, а не собственного контейнера.

| Возможность | Как работает в Reanimator |
|-------------|---------------------------|
| Старт / стоп / рестарт | `systemctl` для `telemt.service`, `docker start/stop/restart` для контейнера, `mtproxymax` для MTProxyMax |
| Логи | `journalctl -u telemt` или `docker logs` цели |
| Ссылки на прокси | из API цели `GET /v1/users` (только IPv4-ссылки; секрет ee-ссылки содержит hex-домен, поэтому ссылки берутся как есть) |
| Трафик, соединения, пользователи | из API цели `/v1/users` (передано, соединения, уник. IP на пользователя) — работает без Prometheus-метрик, которые в telemt по умолчанию выключены |
| Метрики движка | из `metrics_listen`/`metrics_port` цели, если она их отдаёт; иначе MTProxyL предлагает включить их в конфиге цели, подобрав свободный порт |
| Диагностика | проверяет цель: способ управления, порт, конфиг, SNI-домен, API, метрики, применённые фиксы |
| Пользователи цели | правки идут в её конфиг; перед перезапуском MTProxyL сверяет состав и лимиты с тем, что отдаёт API. Сошлось — цель применила всё на ходу, и перезапуск пропускается (соединения не рвутся); не сошлось или API молчит — обычный рестарт |
| Точечный тюнинг | `tune set` правит только указанный ключ в конфиге цели (с бэкапом), не перезаписывая файл целиком |
| Правка конфига | `edit-config` / отдельный пункт главного меню — открывает конфиг цели в `$EDITOR`/nano, делает бэкап и предлагает рестарт только если файл реально изменился |
| Гео-блокировка, NFT, Zapret2, iOS-фиксы, By-MEKO | как обычно — это host-level, владения конфигом не требуют |
| Установка telemt | если цели нет вовсе — запуск официального установщика `telemt/telemt` (`mtproxyl install-telemt`), затем повторный детект и тюнинг |
| Selfmask | заглушка поднимается на хосте, а `[censorship]` цели (`tls_domain`, `mask_host`, `mask_port`, `unknown_sni_action`) патчится точечно, с одним подтверждением и одним рестартом |

Скрыты (нужно владение движком/конфигом): секреты, настройки, движок Telemt,
режим эксперта, бэкапы/миграция, upstream-маршруты и SNI-политика. Пункты меню
нумеруются подряд для каждого режима, поэтому номера в Reanimator и Manager
различаются — ориентируйтесь на названия, а не на номера из скриншотов.

Перед первой правкой чужого конфига MTProxyL делает его резервную копию в
`/opt/mtproxyl/backups/` и печатает путь.

> API цели должен быть включён, иначе ссылки и статистика недоступны:
> ```toml
> [server.api]
> enabled = true
> listen = "127.0.0.1:9091"
> ```
>
> В режиме Manager MTProxyL пишет эту секцию в свой конфиг сам — порт
> спрашивается при установке и меняется в настройках, рядом с портом метрик.
> Указываем `listen` явно: по умолчанию telemt слушает `0.0.0.0:9091`, то есть
> без этой строки REST API движка был бы доступен из интернета.

<a id="pq-warning"></a>

## Выбор домена для FakeTLS

> **Если заглушку ставит MTProxyL** (**[Selfmask](#selfmask-details)**) — поддержка
> постквантового обмена ключами (X25519MLKEM768) обеспечивается самим backend'ом,
> и проверять домен не нужно. Это относится к обоим типам сертификата,
> включая самоподписанный.
>
> **Проверка нужна только для чужого домена**, который вы указываете в
> `tls_domain` вручную: если такой домен не поддерживает PQ, iOS-клиенты могут
> не подключиться (бесконечное «Соединение…»).
>
> **Как проверить:**
> - встроенная утилита: `mtproxyl pq-check ваш-домен.com`
> - меню: **Дополнения → проверить домен на PQ**
> - или бот: [@Sni_checker_bot](https://t.me/Sni_checker_bot)
>
> - 🟢 **сервер принимает X25519MLKEM768** — домен подходит
> - 🟡 **PQ нет, но группа обмена ключами не X25519** — можно использовать
> - 🔴 **PQ не поддерживается + группа обмена ключами = X25519** — **iOS не сможет подключиться**
>
> Проверять умеет любой OpenSSL 3.5.0+, включая системный: если он такой
> версии, ставить ничего не нужно. Где старее — **Дополнения → [3] Установить
> PQ OpenSSL** поставит сборку из состава MTProxyL отдельно от системного пакета.

- [Маршрут до Telegram через WARP](#warp): для серверов, с которых Telegram недоступен

### Мониторинг и бэкапы
- Персистентный трафик, метрики, зашифрованные бэкапы, миграция
- Опциональная база GeoIP: страна, город и провайдер для адресов пользователей

<a id="cli-secrets"></a>

### Секреты (пользователи)

```bash
mtproxyl secret add alice              # Добавить пользователя
mtproxyl secret remove alice           # Удалить
mtproxyl secret list                   # Список с трафиком
mtproxyl secret rotate alice           # Новый ключ
mtproxyl secret enable alice           # Включить
mtproxyl secret disable alice          # Выключить
mtproxyl secret link alice             # Ссылки tg:// (все рабочие виды)
mtproxyl secret clone alice bob        # Клонировать
mtproxyl secret rename alice bob       # Переименовать
mtproxyl secret limits alice           # Лимиты
mtproxyl secret setlimits alice 100 5 10G 2026-12-31
mtproxyl secret adtag alice 0123…      # Своя рекламная метка (32 hex)
mtproxyl secret adtag alice remove     # …и снять её
```

Рекламная метка от [@MTProxybot](https://t.me/MTProxybot) бывает общей и
персональной. Общая живёт в настройках (`AD_TAG`, ключ `ad_tag` секции
`[general]`) и действует на всех; персональная задаётся командой выше, пунктом
«Рекламная метка» в меню пользователей или полем в карточке пользователя в
панели. Она ложится в `[access.user_ad_tags]` и перекрывает общую только для
этого пользователя, остальных не трогая. Работает и в реаниматоре — тогда
секция пишется в конфиг цели. Учитывается движком лишь при включённом
`use_middle_proxy`.

Ссылок на пользователя может быть несколько, и все они рабочие: движок
принимает те виды, что включены в `[general.modes]` его конфига. С включённой
маскировкой это только `ee` (TLS), с выключенной — ещё и `dd` (secure), а в
своём конфиге можно включить и `classic`. Меню «Ссылки на прокси», вывод после
`secret add` и `secret link` показывают их все; QR-код рисуется на первую.
У чужой цели ссылки берутся из её API — ровно те, что telemt печатает в
журнале при запуске.

<a id="cli-settings"></a>

### Настройки

```bash
mtproxyl port 443                      # Изменить порт
mtproxyl ip auto                       # Сбросить IP
mtproxyl domain cloudflare.com         # FakeTLS домен
mtproxyl mask-backend 127.0.0.1:8443   # Mask backend
mtproxyl sni-policy mask               # SNI-политика: mask, drop,
                                       # accept, reject_handshake
mtproxyl config                        # Показать config.toml
```

Те же настройки одним списком — с текущими значениями и проверкой ввода.
Это то, что показывает и правит панель в разделе **Настройки прокси**:

```bash
mtproxyl settings list                 # Все настройки и их значения
mtproxyl settings list --json          # То же машиночитаемо
mtproxyl settings set PROXY_PORT 443   # Изменить (значение проверяется)
```

Доступные ключи: `PROXY_PORT`, `PROXY_DOMAIN`, `CUSTOM_IP`, `AD_TAG`,
`MASKING_ENABLED`, `MASKING_HOST`, `MASKING_PORT`, `UNKNOWN_SNI_ACTION`,
`PROXY_CONCURRENCY`, `FAKE_CERT_LEN`, `PROXY_PROTOCOL`, `PROXY_METRICS_PORT`,
`PROXY_API_PORT`, `BACKUP_RETENTION_DAYS`, `IP_HISTORY_LIMIT`,
`IP_HISTORY_INTERVAL`.

> `IP_HISTORY_LIMIT` — сколько адресов хранить в истории на пользователя,
> по умолчанию 200. Уменьшение подрезает историю на ближайшем обновлении
> списка пользователей. `IP_HISTORY_INTERVAL` — как часто снимать адреса
> в историю, минут (по умолчанию 5, `0` — не снимать). Обе работают в обоих
> режимах: в конфиг движка они не попадают. Остальные — только в Manager
> (`BACKUP_RETENTION_DAYS` в реаниматоре бесполезен: бэкапить чужую цель нечем).

> `CUSTOM_IP` — это адрес для ссылок, а не адрес, на котором слушает движок.
> Задавайте его там, где автоопределение промахивается: NAT, несколько
> адресов, домен вместо IP. Заданное значение попадает в `public_host` конфига
> движка, и конфиг перечитывается сразу.

### GeoIP

Опциональная база: без неё всё работает, просто адреса пользователей

Базы кладутся в `/var/lib/GeoIP/` — стандартный путь, откуда их читает и

<a id="cli-security"></a>

### Безопасность

```bash
mtproxyl geoblock add ir      # Заблокировать страну
mtproxyl geoblock remove ir   # Разблокировать
mtproxyl geoblock list        # Список стран и состояние правил
mtproxyl geoblock reapply     # Переприменить после перезагрузки/смены порта
mtproxyl upstream list        # Upstream-маршруты
mtproxyl upstream add warp socks5 127.0.0.1:40000
```

Аргументы `upstream add`: `<имя> <тип> <адрес> [логин] [пароль] [вес]
[интерфейс] [область]`. Типы — `direct`, `socks5`, `socks4`, `shadowsocks`:

```bash
# Прямой выход через конкретный интерфейс
mtproxyl upstream add eth1 direct "" "" "" 10 eth1

# SOCKS4: пароля в протоколе нет, логин уходит в user_id
mtproxyl upstream add s4 socks4 10.0.0.8:1080 telemt

# Shadowsocks: вместо адреса ss-URL, метод и пароль уже внутри него.
# Работает только при выключенном ME:
#   mtproxyl expert set general use_middle_proxy false
mtproxyl upstream add ss shadowsocks 'ss://2022-blake3-aes-256-gcm:ПАРОЛЬ@10.0.0.1:8388'

# Маршрут только для запросов с тегом me или fetch
mtproxyl upstream add tagged socks5 10.0.0.9:1080 "" "" 20 "" me,fetch
```

**Вес** — 0..65535, доля трафика при случайном выборе среди включённых
маршрутов. **Область** (`scopes`) — теги через запятую: запрос со scope идёт
только через маршруты с этим тегом, а запрос без scope — только через маршруты
с пустой областью. Поэтому хотя бы один включённый маршрут должен оставаться
без области, иначе обычному трафику будет некуда идти — CLI об этом
предупреждает.

Правила гео-блокировки живут в `iptables`/`ipset` и не переживают перезагрузку
сервера, поэтому `geoblock list` показывает не только список стран, но и
реальное состояние правил (и порт, на котором они висят). При смене порта
прокси правила переносятся автоматически.

```bash
mtproxyl dc                   # Дата-центры Telegram: RTT, писатели, покрытие
mtproxyl dc status --json     # То же машинным форматом (панель, бот)
mtproxyl dc threshold 80      # Порог покрытия, % — ниже него бот уведомит
mtproxyl swap status          # Память и файл подкачки
mtproxyl swap on              # Создать и включить подкачку 1 ГБ
mtproxyl swap off             # Выключить и удалить /swapfile

mtproxyl dc threshold off     # Без предупреждений: таблица есть, тревоги нет
                              # Из меню: Дополнения → Дата-центры Telegram

mtproxyl availability status  # Последний вердикт, цель, квота, порог
mtproxyl availability check   # Проверить прямо сейчас
mtproxyl availability details # Вердикт со списком зондов (JSON)
mtproxyl availability on|off  # Проверка по расписанию
mtproxyl availability token X # Токен Globalping (--clear чтобы убрать)
```

У `traffic --json` в ответе два флага, определяющих смысл чисел:

- `directional` — разделён ли трафик на входящий и исходящий. В режиме
  менеджера и при доступных метриках цели — да; API цели отдаёт только общую
  сумму, и тогда `in`/`out` нулевые, а объём лежит в `total`.
- `persistent` — переживают ли числа перезапуск движка. Своя база накопленного
  есть только у менеджера; у чужой цели читаются её счётчики, которые
  обнуляются вместе с ней.

Поле `source` говорит, откуда взяты данные: `db` (база менеджера),
`metrics` (Prometheus цели), `api` (HTTP API цели) или `none`.

Поле `unique_ips` — сколько разных адресов сейчас подключено: у каждого
пользователя своё и общее в `totals`. Это единственное число, которое всегда
берётся из REST API движка, в каком бы режиме мы ни работали: Prometheus
уникальные адреса не считает. Если API недоступен, в JSON приедут нули, а в
меню — «н/д».

<a id="zapret2-details"></a>

## Zapret2 MTProto fix — подробнее

> Новое в v1.2.0. Рекомендуемый метод обхода для серверов под активной блокировкой.
> Ручная установка без менеджера — [zapret2.md](zapret2.md).

### Как работает

| Шаг | Описание |
|-----|---------|
| 1 | В SYN+ACK объявляется окно `1400` вместо реального (десятки КБ), запоминается `ack0` |
| 2 | Клиент не может отправить ClientHello целиком: ядро Linux шлёт в объявленное окно примерно половину — около 700 байт |
| 3 | Этот первый data-пакет режется по `400`: первая часть (400) уходит как есть, вторая (300) — с **битой контрольной суммой**, третья оказывается пустой; оригинал дропается |
| 4 | Для DPI поток рвётся на испорченной части — собрать ClientHello он не может |
| 5 | Остаток ClientHello клиент досылает в зажатое окно `10`, скрипт считает прогресс `delta = th_ack − ack0` |
| 6 | При `delta ≥ 1400` соединение отпускается и помечается `fwmark` — дальше трафик идёт без вмешательства |

Подробный разбор с примером отладочного вывода — в [zapret2.md](zapret2.md).

### iOS bypass

iOS-клиенты определяются по TCP SYN fingerprint и маркируются через `fwmark` — проходят без манипуляций с окном.

### Параметры ядра

Установка и перезапуск выставляют `net.ipv4.tcp_tw_reuse = 1` — файл
`/etc/sysctl.d/99-mtproxyl-zapret2.conf` плюс применение на месте. Без него
клиент за NAT, которому трансляция выдала недавно освободившийся порт, получает
на SYN ответ ACK и висит до таймаута. Прежнее значение возвращается при удалении
zapret2, а что именно выставлено — видно в логе установки.

### Проверка wscale

Реальное TCP окно = `win_ACK × 2^wscale`. Должно быть **< 1400 байт**. Скрипт проверяет это автоматически:

| wscale | 2^wscale | win ACK | Реальное окно |
|--------|----------|---------|---------------|
| 7 | 128 | 10 | 1280 байт ✓ |
| 9 | 512 | 2 | 1024 байт ✓ |
| 11 | 2048 | — | невозможно ✗ |

При `wscale ≥ 11` (буфер 64 МБ+) дробление невозможно ни при каком `win ACK`, и
проверка предлагает применить оптимизацию буфера — `/etc/sysctl.d/99-mtproxyl-wscale.conf`
с `rmem_max`/`wmem_max` 16 МБ. Это даёт `wscale = 9`, после чего `win ACK`
подбирается автоматически (2 → окно 1024 байта).

После применения значения перепроверяются. Если они не изменились, их задаёт
файл, который `sysctl.d` читает позже нашего, — проверка назовёт этот файл.
Предложение появляется при установке, переустановке и в диагностике; когда
оптимизация включена, об этом сказано в шапке меню Zapret2.

### Управление

```bash
mtproxyl                       # Меню → [7] → [2]
mtproxyl nft zapret2           # CLI: установить
mtproxyl nft zapret2-wscale    # Проверить wscale
```

### Дополнительные порты

Кроме порта прокси zapret2 можно навесить на любое число портов и диапазонов —
меню `[7] → [2] → Настройки → Доп. порты`, формат `8443,9000-9100`. Порт прокси
подставляется сам. В `--filter-tcp` уходит список через запятую, в NFT-правила —
анонимный set.

### Область действия правил

Три настройки в том же меню (и в панели, раздел «Лимитер и защита» → Zapret2)
задают, какой именно трафик попадёт в очередь.

**Основной порт** (`ZAPRET2_PORT`) по умолчанию берётся из конфига прокси.
Задайте свой, если клиенты приходят на другой порт — проброс, балансировщик,
собственный DNAT. Пустое значение возвращает порт из конфига.

**Фильтр по IP** (`ZAPRET2_FILTER_IP`) добавляет в правила `ip saddr`/`ip daddr`,
и очередь получает только трафик этого адреса, а не всё, что идёт через тот же
порт. Включён по умолчанию: адрес определяется при установке из таблицы
маршрутов — именно тот, что стоит в заголовках пакетов. За NAT это частный
адрес сервера, а не тот, под которым он виден снаружи; публичный туда
подставлять нельзя — правило не совпадёт ни разу. Принимается только IPv4:
домен в правило nft не встанет, и вся таблица не применится. `off` выключает
фильтр, `auto` определяет адрес заново — пригодится, если адрес сменился.

**Мимо очереди** (`ZAPRET2_EXCLUDE_IFACES`) — интерфейсы, чей трафик проходит
без обработки: список через пробел, можно с `*`. Нужно там, где рядом с прокси
работает VPN: туннели `awg*`, `wg*`, `tun*` несут чужой HTTPS на том же порту
443, и десинк ломает его вместе с нашим — сайты открываются через раз, а
Telegram в туннеле не подключается. Если такие интерфейсы есть на сервере,
установка находит их сама и ставит **ровно те, что нашлись** (`awg0`, а не
маску `awg*`): маска задела бы и туннели, которые появятся потом. В меню
`auto` находит текущие заново, `std` ставит широкий набор `awg* wg* tun*`,
`off` убирает всё. Правила `accept` идут первыми в цепочках
`prerouting`/`postrouting`, до правила с очередью.

```bash
mtproxyl nft set ZAPRET2_PORT 8443
mtproxyl nft set ZAPRET2_FILTER_IP 10.0.0.5
mtproxyl nft set ZAPRET2_EXCLUDE_IFACES "wg* tun*"
mtproxyl nft zapret2-start      # переприменить правила
```

<a id="zapret2-nfqws-client"></a>

### Клиент за домашним роутером с nfqws не подключается

Отдельный случай, который выглядит как поломка прокси: у одного пользователя
подключения нет, у остальных всё работает. Причина не на сервере — на его
роутере (Keenetic, OpenWrt, Padavan и подобные) стоит свой обход блокировок на
том же `nfqws`. Он собирает ClientHello из TCP-сегментов, чтобы разобрать SNI,
а zapret2 намеренно шлёт этот ClientHello рваным и с битой контрольной суммой —
клиентский `nfqws` не может его собрать и портит соединение уже со своей
стороны. Помогает любое из двух, оба делаются **на роутере**:

- Добавить в параметры запуска `nfqws` **`--reasm-disable=tls_client_hello`** —
  сборка ClientHello выключается, и рваный поток проходит насквозь.
- Внести домен, под который маскируется прокси (тот же, что в FakeTLS SNI), в
  **исключения** `nfqws` — тогда до этого адреса роутер не вмешивается вовсе.

Второй вариант точечнее: обход на роутере продолжает работать для всего
остального. Проверить догадку проще всего, временно выключив обход на роутере
целиком — если прокси сразу заработал, дело в нём.

### Docker bridge

Если цель (режим Reanimator) живёт в Docker с bridge-сетью, трафик до неё идёт
через `forward`, а не через `prerouting`/`postrouting` хоста — правила
применяются в цепочке `forward`. Есть два варианта фильтрации:

| Стратегия | Правило | Когда |
|-----------|---------|-------|
| `simple` *(по умолчанию)* | только по портам, без `ip daddr/saddr` | надёжнее, watcher не нужен |
| `precise` | дополнительно сужается до IP контейнера | точнее; ставится watcher, т.к. IP контейнера меняется при пересоздании |

Выбор предлагается при установке и меняется позже в настройках zapret2.

**API цели в bridge-сети.** Частая жалоба: в конфиге стоит `[server.api]
enabled = true`, а MTProxyL пишет «API не отвечает». Причина в том, что
`listen = "127.0.0.1:9091"` внутри контейнера — это петля самого контейнера, и
с хоста туда не попасть ни при каких портах. Лечится одним из двух:

- привязать API ко всем адресам контейнера и разрешить сеть docker в белом
  списке — MTProxyL сам пойдёт на адрес контейнера:

  ```toml
  [server.api]
  enabled = true
  listen = "0.0.0.0:9091"
  whitelist = ["127.0.0.0/8", "172.16.0.0/12", "10.0.0.0/8"]
  ```

  Наружу это ничего не открывает: порт контейнера доступен только хосту, пока
  не опубликован через `-p`. А вот про `whitelist` забывают чаще всего — со
  списком по умолчанию (`127.0.0.0/8`) движок отклоняет запросы уже после
  подключения, потому что приходят они с адреса docker-сети;
- либо опубликовать порт на петлю хоста: `-p 127.0.0.1:9091:9091`. Адрес тогда
  остаётся привычным `127.0.0.1` и не меняется при пересоздании контейнера —
  для панели это удобнее, её `telemt.url` записан в конфиге.

Диагностика (`mtproxyl health`, экран трафика, меню ссылок) показывает этот
разбор сама, когда видит цель в bridge и недоступный API.

<a id="selfmask-details"></a>

## Selfmask — маскировка под реальный сайт

Selfmask превращает прокси-сервер в полноценный HTTPS-сайт на собственном домене.

Заглушку поднимает сам MTProxyL, поэтому поддержка PQ hybrid (X25519MLKEM768)
обеспечена backend'ом и проверять домен не нужно. Проверка на PQ нужна только
если вы используете **чужой** домен для FakeTLS — для этого есть меню
**Дополнения → проверка домена на PQ** или бот `@Sni_checker_bot`.

### Как работает

```
Telegram клиент → telemt :443 (MTProto)
Браузер / сканер → telemt :443 → mask → PQ nginx 127.0.0.1:8444 → ваш сайт
```

### Тип сертификата

| Режим | Когда выбирать | Требования |
|-------|----------------|------------|
| `letsencrypt` | Есть реальный домен, указывающий на этот сервер | A-запись + свободный порт 80 (ACME) |
| `selfsigned` | Домена нет или он несуществующий/чужой | Ничего: ни DNS, ни порта 80 |

В режиме `selfsigned` сертификат выписывается на 10 лет на любой указанный
домен, порт 80 не занимается (ACME и http→https redirect не нужны), а системный
nginx/панель на 80 порту не трогаются. Заглушка отдаётся только по SNI на
mask-backend, поэтому «снаружи» домен не открывается — это ожидаемое поведение.

### Что устанавливается

| Компонент | Путь | Описание |
|-----------|------|----------|
| PQ nginx | `/opt/mtproxyl-nginx/sbin/nginx` | nginx 1.28.3 + OpenSSL 3.5.7 (статический) |
| PQ OpenSSL | `/opt/mtproxyl-nginx/bin/openssl` | Для PQ-проверок |
| Конфиг | `/opt/mtproxyl-nginx/conf/nginx.conf` | Генерируется автоматически |
| Сайт | `/var/www/mtproxyl-selfmask/` | HTML-заглушка или шаблон |
| Сертификат (LE) | `/etc/letsencrypt/live/<домен>/` | Let's Encrypt (автопродление) |
| Сертификат (self) | `/opt/mtproxyl-nginx/selfsigned/<домен>/` | Самоподписанный, 10 лет |
| Служба | `mtproxyl-pq-nginx.service` | Systemd unit |

### Шаблоны сайтов

| Шаблон | Описание |
|--------|----------|
| Простая заглушка | «Сайт временно недоступен» |
| Файловый менеджер | Форма входа (всегда «неверные данные») |
| Cat Runner | Мини-игра: кот прыгает через кактусы |
| Свой URL | Любой `index.html` по ссылке |
| Свой сайт с сервера | Путь к папке с `index.html` — копируется целиком |

Последний вариант для тех, у кого сайт уже лежит на диске: укажите
`/var/www/some.name.ru` (или путь к самому `index.html` — возьмём его папку), и
содержимое скопируется в каталог заглушки со всеми стилями, скриптами и
картинками. Поднимать раздачу не нужно. Путь проверяется сразу — если его нет
или в нём нет `index.html`, мастер скажет об этом, а не подставит заглушку.

> Из панели путь задаётся там же, где шаблоны, — пункт «Свой сайт из папки на
> сервере». Каталоги внутри `/tmp` она не увидит: у её службы `PrivateTmp=true`,
> и `/tmp` у неё свой. Для сайта это не ограничение — держите его в `/var/www`.

<a id="availability"></a>

## Доступность из России

Отвечает на вопрос, который сервер о себе задать не может: «а доходят ли до
меня пользователи?». Публичная сеть зондов **Globalping** выполняет
HTTPS-рукопожатие с портом прокси с российских резидентских (eyeball) сетей —
именно оттуда, где действует фильтрация по подписчикам, а не дата-центровский
зонд, которому сервер отвечает независимо от блокировок в стране. Успех — это
полученный TLS-сертификат, то же рукопожатие, что делает клиент Telegram, а не
просто открывшийся TCP-порт: порт, который отвечает, но рвёт сессию на
середине, так тоже ловится.

Проверка идёт обычными исходящими запросами к Globalping API — ставить на
сервер ничего не нужно. Работает в обоих режимах.

Меню: **Дополнения → Доступность из России**. Результат один и тот же для меню,
[веб-панели](#panel) и [телеграм-бота](#tgbot) — считает его сам MTProxyL,
таймером `mtproxyl-availability.timer`, поэтому проверки идут и при закрытом
браузере, и при выключенном боте.

```bash
mtproxyl availability status        # Вердикт, цель, квота, порог
mtproxyl availability check         # Проверить сейчас (не чаще раза в минуту)
mtproxyl availability on            # Проверка по расписанию
mtproxyl availability off           # Только вручную
mtproxyl availability token <токен> # Квота 250 → 500 кредитов в час
```

| Настройка | По умолчанию | Что делает |
|---|---|---|
| `AVAILABILITY_ENABLED` | `true` | Проверка по расписанию. Ручная работает всегда |
| `AVAILABILITY_INTERVAL` | `15` | Период проверки, минут |
| `AVAILABILITY_PROBES` | `20` | Зондов на проверку, максимум 50 |
| `AVAILABILITY_THRESHOLD` | `50` | Ниже этого процента бот пришлёт предупреждение |
| `AVAILABILITY_HOST` | пусто | Адрес проверки; пусто — определяется сам |
| `AVAILABILITY_PORT` | пусто | Порт проверки; пусто — порт прокси |
| `AVAILABILITY_SNI` | пусто | SNI; пусто — домен FakeTLS |

Адрес по умолчанию берётся так: домен Selfmask, если заглушка поднята, иначе
прикреплённый к ссылкам `CUSTOM_IP`, иначе внешний адрес сервера. Задавать
вручную нужно там, где сервер сам себя определяет не так, как видят клиенты:
NAT, несколько адресов, CDN перед прокси.

**Квота.** Globalping отпускает 250 кредитов в час, один зонд — один кредит;
бесплатный токен с [dash.globalping.io](https://dash.globalping.io/) поднимает
лимит до 500. Значения по умолчанию (20 зондов раз в 15 минут) — это 80
кредитов в час, остальное остаётся на ручные проверки. MTProxyL считает
потраченное скользящим часом и не заказывает проверку, которая в остаток не
влезает; если лимит объявит сам сервис ответом 429, его слово важнее — до
названного им времени проверки не идут. Токен хранится отдельным файлом
`/opt/mtproxyl/availability/token` с правами 600, а не в `settings.conf`,
который читается всем миром.

<a id="warp"></a>

## Telegram через WARP

Для серверов, с которых серверы Telegram недоступны. В туннель Cloudflare WARP
уходит **не весь трафик сервера, а только подсети Telegram**: клиенты приходят
на прокси по-прежнему напрямую, обратный путь не меняется. Правила живут в
ядре, поэтому работает во всех трёх режимах — свой telemt у менеджера, чужая
цель у реаниматора и посторонний прокси в «только оптимизации».

Эндпоинты Cloudflare ищет [warpscout](https://github.com/vernette/warpscout):
он поднимает настоящий туннель к каждому кандидату и спрашивает, где тот
выходит. Бинарник скачивается из релиза оригинального проекта, а если он
недоступен или не понимает нужные ключи — из нашей сборки, лежащей ассетом
релиза MTProxyL.

```bash
mtproxyl warp status            # Состояние, выход, службы, счётчик пакетов
mtproxyl warp on socks          # Вариант A: SOCKS5 warpscout + redsocks
mtproxyl warp on iface          # Вариант B: интерфейс WireGuard
mtproxyl warp on upstream       # Вариант C: socks5-upstream движка, без правил
mtproxyl warp off               # Выключить, вернуть прямой ход
mtproxyl warp scan              # Разведка: найти лучший эндпоинт
mtproxyl warp location DE,NL    # Где выходить (clear — лучший по задержке)
mtproxyl warp endpoint A:PORT   # Закрепить адрес (clear — искать разведкой)
mtproxyl warp proto awg|wg|masque
mtproxyl warp hint              # Что дописать в конфиг чужой цели (вариант C)
mtproxyl warp reapply           # Обновить список подсетей и правила
```

Меню: **Безопасность и маршрутизация → Telegram через WARP**. В панели —
раздел «Telegram через WARP». Включённый маршрут виден строкой в главном меню.

### Какой вариант выбрать

**Вариант A — SOCKS5 warpscout + redsocks.** Туннель поднимает сам warpscout в
пользовательском пространстве, ядро ни при чём. Умеет обфускацию (`awg`,
`masque`) — проходит там, где обычный WireGuard режут по сигнатуре
рукопожатия. Подводные камни: туннель один, без запасного узла — после обрыва
службу поднимает systemd и заново ищет эндпоинт, это минута-другая; в тракте
лишний процесс redsocks; заворачивается только TCP (для MTProto хватает).

**Вариант B — интерфейс WireGuard + policy routing.** Обычный wg-туннель в
ядре, маршрут выбирается по метке. Переподключается сам, лишних процессов нет.
Подводные камни: только чистый WireGuard — там, где его блокируют по сигнатуре,
рукопожатия не будет вовсе; нужен модуль ядра `wireguard` и `wireguard-tools`.

**Вариант C — socks5-upstream в конфиге движка.** Правил в ядре нет вовсе:
warpscout поднимает SOCKS5, а telemt ходит через него по своей записи
`[[upstreams]]`. В режиме менеджера MTProxyL прописывает маршрут сам; у чужой
цели реаниматора он поднимает туннель и печатает, что дописать в её конфиг
(`mtproxyl warp hint` покажет это в любой момент), а если цель в docker bridge
— подставляет адрес шлюза вместо петли и закрывает порт правилом. Подводные
камни: через socks уходит **весь**
исходящий трафик движка, включая загрузку TLS-метаданных с локального
mask-бэкенда, которая внутри туннеля недостижима — MTProxyL сам возвращает её
на прямой маршрут отдельной областью (`censorship.tls_fetch_scope` плюс
`direct`-маршрут с этой областью).

Свои маршруты без области MTProxyL предлагает выключить на время работы WARP и
включает обратно при `warp off`: запрос без области движок отправляет в любой
маршрут без области, выбирая по весу, — оставленный `direct` увёл бы часть
соединений мимо туннеля.

Проще так: свой telemt — берите C; чужая цель реаниматора, посторонний прокси
или tools-only — B, а если разведка не находит живых эндпоинтов (значит wg
режут по сигнатуре) — A.

### Middle proxy с WARP не работает

Ключи ME-рукопожатия обе стороны выводят из адреса **и порта**, с которых прокси
пришёл к Telegram. Выход WARP — общий CGNAT Cloudflare: он меняет порт и даже
адрес от соединения к соединению. Проверено тремя способами:

- с включённым ME покрытие дата-центров падает до нуля и не поднимается;
- подстановка выходного адреса в `middle_proxy_nat_ip` не спасает — порт чужой;
- конфигурация по мануалу движка (`direct`-upstream с `bind_addresses` на адрес
  туннеля плюс отдельная таблица маршрутов, при которой STUN-рефлексия
  становится bind-aware) тоже не поднимает писателей: за несколько минут
  рефлексия увидела три разных выходных адреса Cloudflare
  (`104.28.163.194`, `104.28.219.140`, `104.28.251.139`).

То есть дело не в настройке, а в самом характере выхода WARP: постоянного
соответствия «адрес:порт» у него нет. Для ME нужен выход, который его сохраняет
— свой сервер с публичным адресом (SOCKS5, который честно отдаёт `BND.ADDR`,
или туннель до него с port-preserving SNAT).

Поэтому MTProxyL отказывается включать WARP, пока у движка включён
`use_middle_proxy`, и предлагает переключить его на прямую маршрутизацию
(в режиме менеджера — сам, в реаниматоре — покажет, что поправить в конфиге
цели). Цена — рекламная метка (спонсорский канал) перестаёт действовать: она
живёт только в режиме ME. Там, где Telegram и так недоступен, терять нечего:
без связи с дата-центрами метка всё равно не работает.

### Где выходить

По умолчанию берётся живой эндпоинт с наименьшей задержкой. Второй вариант —
задать локацию: коды стран двумя буквами (`DE`, `NL`, `FI`, `SE`, `TR`) или
коды узлов Cloudflare тремя, по коду аэропорта (`FRA`, `AMS`, `HEL`, `ARN`).
Через запятую, можно смешивать: `DE,AMS`. Чем уже список, тем выше шанс, что
живых эндпоинтов не найдётся вовсе.

Подсети Telegram берутся из официального списка
`https://core.telegram.org/resources/cidr.txt`; если он недоступен (а недоступен
он ровно там, где всё это и нужно), используется встроенный. Обновить —
`mtproxyl warp reapply`.

Что маршрут действительно работает, видно по двум вещам: Cloudflare в ответе
`cdn-cgi/trace` подтверждает `warp=on`, а счётчик nft показывает, сколько
пакетов до Telegram ушло в туннель. Связь с дата-центрами после включения
проверяется командой `mtproxyl dc`.

<a id="tgbot"></a>

## Телеграм-бот

Управление прокси кнопками прямо в Telegram. Бот — обёртка над этим же CLI:
всё, что он делает, делается теми же командами `mtproxyl`, что и из меню.

Предлагается при первой установке (по умолчанию «нет» — нужен токен) и в любой
момент из главного меню: пункт **«Телеграм бот»**. Оттуда же настройка,
обновление и удаление.

```bash
mtproxyl tgbot install     # Установить или переустановить
mtproxyl tgbot setup       # Задать токен и администратора заново
mtproxyl tgbot status      # Состояние и последние строки журнала
mtproxyl tgbot admin-add 12345678
mtproxyl tgbot logs 100
mtproxyl tgbot uninstall
```

### Что нужно для установки

1. **Токен.** В Telegram откройте **@BotFather**, отправьте `/newbot`,
   придумайте имя и username — BotFather пришлёт строку вида
   `1234567890:AAH…`. Установщик проверит её у Telegram сразу.
2. **Кто управляет.** Откройте своего бота и отправьте ему `/start` —
   установщик увидит ваш ID сам. Если не вышло, ID подскажет `@userinfobot`.

### Что умеет

| Раздел | В обоих режимах |
|---|---|
| Прокси | запуск, остановка, перезапуск, состояние |
| Статус | порт, домен, аптайм, соединения, уникальные адреса, трафик |
| Дата-центры | `/dc`: RTT, писатели и покрытие по каждому DC, уведомление при просадке |
| Пользователи | добавить, удалить, включить, выключить, переименовать |
| Лимиты | соединения, адреса, квота трафика, срок действия |
| Ссылки | выбор пользователя, кликабельная `tg://`-ссылка и QR-код |
| Трафик | таблицей: объём, соединения и уникальные адреса на пользователя |
| Доступность | вердикт, разбор по зондам, проверка, период, порог, квота |

Если серверы Telegram с хоста недоступны напрямую, боту можно дать локальный
SOCKS5 — пункт «Прокси для Telegram» в меню бота, карточка на его странице в
панели или `mtproxyl tgbot set proxy socks5://127.0.0.1:1080` (`off` — обратно
напрямую). Сам прокси поднимаете вы: MTProxyL его не ставит и за ним не следит.
Схема принимается только `socks5://`; для неё в venv бота ставится
`aiohttp-socks`, он приезжает вместе с обновлением кода бота.

В режиме менеджера добавляются **бэкапы**: собрать и прислать архив в чат,
автобэкап по расписанию (по умолчанию 05:30, файл в чат — по желанию).

Все команды перечислены в `/help`, главное меню — `/menu`.

Меню в чате **одно и всегда внизу**: следующий экран занимает то же сообщение,
а когда меню нужно подвинуть — старое удаляется и появляется новое под
последним сообщением. Ссылка с QR-кодом и результат проверки доступности — тоже
экраны меню. Команды и ответы на вопросы бот убирает из переписки, поэтому в
истории остаётся только то, ради чего в неё заглядывают: уведомления
наблюдателей и файлы бэкапов. Списки пользователей, трафика и зондов
показываются таблицами.

### Уведомления

Приходят при **смене состояния**, а не на каждой проверке: «прокси лежит» раз
в пять минут перестают читать через час.

- доступность из России упала ниже порога — и когда вернулась;
- покрытие дата-центров Telegram упало ниже порога — и когда вернулось;
- прокси перестал отвечать — и когда поднялся;
- у пользователя кончилась квота или истёк срок;
- итог автобэкапа (режим менеджера).

Порог по дата-центрам общий на бота, панель и меню — он живёт в настройках
MTProxyL (`DC_THRESHOLD`, по умолчанию 80%). Меняется в трёх местах: пунктом
«Порог покрытия дата-центров» в **Телеграм бот → Уведомления**, в карточке
дата-центров на дашборде панели и командой `mtproxyl dc threshold`. Ноль (он же
`off`) выключает предупреждения целиком: таблица и цифры остаются, но о
просадке не скажет ни бот, ни панель.

Что присылать и как часто сверяться — в меню бота (`/settings`) и в меню
MTProxyL: **Телеграм бот → Уведомления и таймеры**.

### Как устроен

Ставится в `/opt/mtproxyl-tgbot`: python в venv, служба `mtproxyl-tgbot`,
настройки в `config.json` с правами 600. Нужно около 300 МБ на диске и пакеты
`python3-venv`, `curl`, `qrencode`; установщик ставит их сам. Единственный
необязательный — `qrencode`: без него ссылка придёт без QR-кода, всё остальное
работает. Работает от собственной учётной
записи `mtproxyl-tgbot` без входа в систему — **не от root**. К MTProxyL ходит
через `sudo` по поимённому списку подкоманд в `/etc/sudoers.d/mtproxyl-tgbot`:
разрешено ровно то, что бот действительно зовёт.

Отвечает бот только тем, чьи ID перечислены администраторами; список читается
на каждом сообщении, поэтому добавленный из меню получает доступ сразу, без
перезапуска службы.

Код бота обновляется вместе со скриптом: `mtproxyl update` перекачивает его,
переписывает права sudo и перезапускает службу.

### Из панели

Всё то же есть в [веб-панели](#panel), раздел **Телеграм-бот** — в обоих
режимах: состояние и журнал службы, установка формой (токен и ваш Telegram ID),
запуск, остановка, обновление кода, уведомления и периоды проверок, автобэкап,
список администраторов и удаление. Установка идёт фоном, с тем же журналом по
шагам, что и остальные долгие операции: venv и aiogram ставятся пару минут.

<a id="panel"></a>

## Веб-панель MTProxyL-Panel

Опциональный веб-интерфейс ко всему, что умеет MTProxyL: пользователи, трафик,
переключение режимов, Selfmask, лимитер, Zapret2, блокировка стран, маршруты и
бэкапы. Интерфейс на русском, ставится одним бинарником.

У каждого пользователя видны накопленный трафик и история подключённых IP —
в обоих режимах. Если поставить базу GeoIP (кнопка в разделе **Дополнения**),
рядом с адресами появятся страна, город и провайдер.

Раздел **Доступность из России** показывает, что видит проверка из
[«Дополнений»](#availability): дошли ли российские зонды до прокси и какие
именно не дошли.

Панель не заменяет MTProxyL, а работает поверх него — CLI и меню остаются
основным способом управления.

### Установка

Ставится **после** того, как прокси поднят: панели нужен работающий движок
с доступным API.

```bash
mtproxyl panel install
```

Либо через меню: **Дополнения → Веб-панель MTProxyL-Panel**.

Отдельно, без MTProxyL:

```bash
curl -fsSL https://raw.githubusercontent.com/Liafanx/MTProxyL/main/mtproxyl-panel/install.sh -o install-panel.sh
sh install-panel.sh install
```

Порт спрашивает установщик (по умолчанию 8080), после установки панель
доступна на `https://<ваш-сервер>:8080`.

Установщик отдельно спрашивает, куда привязывать сокет: на все интерфейсы или
только на `127.0.0.1`. Во втором случае панель снаружи недоступна — порт не
слушается вовсе, брутфорсить нечего, — а ходят в неё через ssh-туннель:

```bash
ssh -L 8080:127.0.0.1:8080 <пользователь>@<ваш-сервер>
# и открыть http://127.0.0.1:8080 в своём браузере
```

Шифрование в этом режиме не настраивается: канал до браузера шифрует сам ssh, а
по петле трафик машину не покидает.

> Панель выпускается отдельно от MTProxyL — её релизы помечены тегом
> `mtproxyl-panel-vX.Y.Z`. Пока такого релиза нет, панель можно собрать прямо
> из ветки: `sh install-panel.sh install --from-source=dev`. При наличии Docker
> сборка идёт в нём и не оставляет тулчейн на сервере; иначе понадобятся
> Go 1.25+ и Node.js 20+. `mtproxyl panel install` предложит это сам.

### Управление

```bash
mtproxyl panel status      # состояние
mtproxyl panel restart     # перезапуск
mtproxyl panel disable     # выключить, не удаляя
mtproxyl panel enable      # включить обратно
mtproxyl panel uninstall   # удаление (спросит, оставить ли конфиг и данные)
```

`disable` останавливает службу и снимает её с автозапуска — после
перезагрузки панель не поднимется. Бинарник, конфиг, пароль и сертификаты
остаются на месте, `enable` возвращает всё как было. То же в меню:
**Дополнения → Веб-панель**, пункт «Выключить (без удаления)».

Отдельно, без MTProxyL — тем же `install.sh`, что и для установки:

```bash
curl -fsSL https://raw.githubusercontent.com/Liafanx/MTProxyL/main/mtproxyl-panel/install.sh | sudo sh -s -- uninstall
curl -fsSL https://raw.githubusercontent.com/Liafanx/MTProxyL/main/mtproxyl-panel/install.sh | sudo sh -s -- purge
```

`-s --` в пайпе обязателен именно в таком виде — без `-s` `sh` попытается
открыть `uninstall`/`purge` как файл, а не передаст их установщику аргументом.
`uninstall` оставляет конфиг и данные (в них логин и хеш пароля — повторная
установка найдёт их и пропустит мастер), `purge` убирает всё, включая
системного пользователя. Подробнее — [mtproxyl-panel/README.md](mtproxyl-panel/README.md#удаление-без-mtproxyl).

### Права

Панель работает под собственным непривилегированным пользователем
`mtproxyl-panel`. Для команд, которым нужен root, установщик создаёт
`/etc/sudoers.d/mtproxyl-panel-mtproxyl` — список **конкретных** разрешённых
команд, а не право запускать `mtproxyl` целиком. При отключении интеграции или
удалении панели файл убирается.

Список именной, поэтому команда, появившаяся в новой версии, работать не
начнёт, пока файл не перепишут: панель, обновлённая своей же кнопкой, меняет
только бинарник. Если она сообщает, что ей не хватает прав sudo, — обновите
их командой `mtproxyl panel install`.

### Ограничения

- Обновление движка telemt из панели недоступно: встроенный механизм рассчитан
  на systemd-сервис, а в режиме Manager движок работает в Docker. Используйте
  `mtproxyl engine`.
- Интерактивный мастер `selfmask setup` остаётся только в CLI: из панели
  параметры задаются по отдельности и применяются командой `selfmask apply`.
- Один администратор, без ролей и 2FA.
- Бэкапы, маршруты, экспертные параметры и супер эксперт доступны только в
  режиме Manager — в Reanimator они скрыты, так как требуют владения конфигом.
- Проверка ограничений сервера (censorcheck) в панель не перенесена: она
  выполняет сторонний скрипт из сети. Команда осталась в меню MTProxyL.
- **Ubuntu 26+:** если установка падает на `visudo: invalid sudoers file` /
  `wildcards are not allowed in command arguments` — система переключена на
  sudo-rs, чей `visudo` пока не поддерживает `*` в аргументах sudoers.
  `sudo update-alternatives --set sudo /usr/bin/sudo.ws` возвращает
  классический sudo, после чего установка проходит.

Подробности — [mtproxyl-panel/README.md](mtproxyl-panel/README.md).

<a id="ios-fixes"></a>

## Устаревшие iOS фиксы

> Доступны через меню `[7] NFT → [12] Устаревшие настройки`.
> При использовании **Zapret2 fix** или **Smart By-MEKO** эти фиксы не нужны.

### Вариант 1 — TCP keepalive

Ускоряет обнаружение мёртвых сокетов через `sysctl`.

### Вариант 2 — MSS + redirect

Отдельный порт для iOS с MSS=92. Только для Classic режима.

### Оптимизация системы By-MEKO

TCP keepalive 45s, BBR, расширенные очереди. Меню: `[7] → [11]`.

<a id="expert-details"></a>

## Режим эксперта — подробнее

Управление **любыми** параметрами telemt `config.toml` через каталог с валидацией.

Приоритет: `config.toml → tunings.conf → expert.conf`

Поддерживаемые секции: `general`, `general.modes`, `general.links`, `general.telemetry`, `network`, `server`, `server.listeners`, `server.conntrack_control`, `server.api`, `timeouts`, `censorship`, `censorship.tls_fetch`, `access`, `logging`

### Режим супер эксперта

Крайняя форма: конфиг движка вы ведёте сами, MTProxyL его не генерирует.

Включается в главном меню («Режим супер эксперта») или командой `mtproxyl superexpert on`.
При первом включении `/opt/mtproxyl/superexpert.toml` создаётся копией текущего рабочего
конфига — дальше правите файл вручную. Перед каждым запуском прокси он копируется на место
`config.toml`, поэтому изменения применяются обычным перезапуском.

Пока режим включён, менеджер в конфиг ничего не дописывает: «Управление секретами»,
«Настройки», «Режим эксперта», `tune set` и `expert set` блокируются — пользователи,
порт, домен и всё остальное задаются в вашем файле. Настройки хоста (NFT, Zapret2,
selfmask, гео-блокировка, бэкапы) работают как обычно, а порт из вашего конфига
подхватывается в настройки MTProxyL, чтобы правила и ссылки остались на нужном порту.

При выключении файл сохраняется: при следующем включении используется он же. Файл
попадает в бэкапы и в миграцию. В главном меню при включённом режиме выводится
«Режим супер эксперта включён».

## Модульная архитектура

```
/opt/mtproxyl/
├── mtproxyl.sh                  # Главный скрипт + CLI dispatcher
├── lib/
│   ├── colors.sh                # UI: цвета, символы
│   ├── utils.sh                 # Утилиты, валидация, CLI-обработчики
│   ├── settings.sh              # Настройки
│   ├── detect.sh                # Reanimator: детект чужого telemt + точечный тюнинг
│   ├── secrets.sh               # Секреты пользователей
│   ├── config.sh                # Генерация config.toml
│   ├── docker.sh                # Docker
│   ├── engine.sh                # Версии telemt
│   ├── traffic.sh               # Метрики, трафик, история IP пользователей
│   ├── geoblock.sh              # Гео-блокировка
│   ├── geoip.sh                 # База GeoIP: страна, город, провайдер
│   ├── upstream.sh              # Upstream
│   ├── warp.sh                  # Маршрут до Telegram через WARP (warpscout)
│   ├── backup.sh                # Бэкапы
│   ├── nft.sh                   # NFT limiter + Zapret2 fix + iOS фиксы
│   ├── selfmask.sh              # Selfmask (PQ nginx + LE / самоподписанный cert)
│   ├── panel.sh                 # Установка и управление веб-панелью
│   ├── expert_catalog.sh        # Каталог параметров telemt
│   ├── expert_mode.sh           # Режим эксперта
│   ├── settings_cli.sh          # Машинный вывод настроек для панели
│   ├── tui_main.sh              # Главное меню
│   ├── tui_proxy.sh             # Подменю: прокси
│   ├── tui_secrets.sh           # Подменю: секреты
│   ├── tui_links.sh             # Подменю: ссылки
│   ├── tui_settings.sh          # Подменю: настройки
│   ├── tui_security.sh          # Подменю: безопасность
│   ├── tui_traffic.sh           # Подменю: трафик
│   ├── tui_engine.sh            # Подменю: движок
│   ├── tui_backup.sh            # Подменю: обновления и бэкапы
│   ├── tui_expert.sh            # Подменю: режим эксперта
│   ├── tui_nft.sh               # Подменю: NFT + Zapret2
│   ├── tui_selfmask.sh          # Подменю: selfmask
│   ├── tui_addons.sh            # Подменю: дополнения
│   ├── tui_warp.sh              # Подменю: Telegram через WARP
│   ├── tui_detect.sh            # Подменю: цель / режим (Reanimator)
│   └── install.sh               # Установщик + деинсталлятор
├── mtproxy/config.toml          # Конфиг telemt
├── settings.conf                # Настройки MTProxyL
├── secrets.conf                 # Секреты
├── expert.conf                  # Expert override
├── tunings.conf                 # Быстрый тюнинг
├── nft-rules.conf               # NFT настройки (включая Zapret2)
└── backups/
```

Веб-панель — отдельный компонент в каталоге `mtproxyl-panel/` этого
репозитория: Go + React, собирается в один бинарник со встроенным фронтендом,
ставится своим установщиком. MTProxyL вызывает её установщик и показывает
состояние, но логику установки не дублирует.

```bash
mtproxyl uninstall
```
