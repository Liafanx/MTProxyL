Все изменения проекта документируются в этом файле.

## v1.6.0 — 27.08.2026

Панель — **1.1.0**.

### Добавлено

- **WEB Proxy.** Тип прокси `WEB` из Telegram Desktop: MTProto внутри обычного HTTPS
  или WebSocket. Включается командой `mtproxyl web enable`. Домен, сертификат и
  сайт-заглушку WEB берёт у Selfmask: имя добавляется в существующий сертификат
  отдельным SAN, второй выпуск не нужен. Требует движок 3.5.1 или новее.

  Раскладок две. `shared` — WEB и FakeTLS делят публичный порт, nginx разбирает SNI
  и разводит их по разным бэкендам; обе ветки идут с PROXY protocol, так что
  настоящий адрес клиента до движка доезжает. Здесь домен WEB обязан отличаться от
  домена маскировки — FakeTLS-клиент шлёт в SNI именно её домен, и совпадение увело
  бы клиентов в nginx вместо движка; по умолчанию берётся поддомен
  `web.<домен Selfmask>`. Нужен nginx со `stream` и `ssl_preread`.

  `split` — у WEB свой порт, движок остаётся на `PROXY_PORT` напрямую: `ssl_preread`
  не нужен, лишнего хопа у обычного прокси нет, домены могут совпадать, а **zapret2
  и SYN-лимитер фильтруются по порту прокси и WEB не задевают вовсе**.

  Команды: `web status`, `web enable`, `web disable`, `web links`, `web set`,
  `web settable`, `web json`. Транспорт по умолчанию **`websocket-lanes`** — он
  единственный, кто нормально работает вместе с zapret2; доступны также
  `https-lanes`, `https` и `websocket`. Отладочная страница `/web-status`
  включается через `WEB_DEBUG`.

  Ставится и аргументами: `--web`, `--web-layout`, `--web-domain`, `--web-carrier`,
  `--web-port`, `--web-secret-mode`. Генератор команды переезда добавляет их сам,
  так что на новом сервере WEB поднимается вместе с остальным. В меню
  «Дополнения» появился свой экран.

- **Меню WEB Proxy переехало в главное меню**, пятым пунктом после «Настроек», а
  в шапке появилась строка с состоянием и доменом. Из «Дополнений» пункт убран.

- **Ссылка `tg://webproxy` теперь везде, где остальные**: на экране «Ссылки на
  прокси», в разделе пользователей панели и в боте. В боте она к тому же стала
  кликабельной — раньше дополнительные ссылки шли только текстом для копирования.

- **Reanimator умеет WEB на чтение.** Конфигом владеет хозяин цели, поэтому
  MTProxyL там ничего не включает, но читает `[web]` из конфига цели и собирает
  ссылки по её секретам.

- **Предупреждение про zapret2.** Он зажимает TCP-окно в SYN+ACK, когда SNI ещё
  неизвестен, и режет скорость https-carrier'ов; исключить домен нельзя в
  принципе. `websocket-lanes` это переживает — после Upgrade там один долгий
  сокет на поток, а не поток коротких запросов, — поэтому он и стоит по
  умолчанию. Предупреждение показывается только там, где проблема настоящая:
  carrier из семейства `https`, раскладка `shared` и активный zapret2.

- **`mtproxyl status --json` отдаёт поле `web`** — включён ли режим, домен, раскладка
  и транспорт. Оттуда его берут бот и панель, так что состояние WEB видно, не
  открывая отдельный раздел.

- **Панель и бот знают про WEB.** В панели появился раздел «WEB Proxy»: состояние,
  раскладка, транспорт, порты, список причин, мешающих включению, редактор
  параметров и ссылки. Включение и выключение идут через общий раннер операций,
  как переключение режима. Бот получает `tg://webproxy` вместе с обычными
  ссылками и подписывает их отдельно — раньше он принял бы такую ссылку за
  `dd · secure` и подменил бы её несуществующим адресом на `t.me`.

- **Экспертный каталог знает WEB.** Добавлены таблицы `web.limits`, `web.timeouts`
  и `web.debug` — 40 параметров с честной пометкой hot-reload: timeouts и debug
  применяются на лету, limits принадлежат процессу и требуют перезапуска движка.

### Исправлено

- **`mtproxyl selfmask pq-nginx` — новая команда: обновляет nginx до сборки из
  состава MTProxyL, что бы ни стояло сейчас.** Прежняя установка молча пропускала
  обновление, если бинарник уже был на месте или системный nginx умел PQ, — а для
  WEB нужен именно наш, со `stream` и `ssl_preread`. Команда заодно пересобирает
  конфиг: архив разворачивается поверх префикса и приносит свой `nginx.conf`,
  затирая настроенный.

- **Панели не хватало прав на команды `web`** — раздел падал с «sudo: a password
  is required». Права выдаются установщиком панели, обновляются через
  `mtproxyl panel install`.

- **Бот отдавал нерабочую WEB-ссылку.** Он принимал её за `dd · secure` по началу
  секрета и подменял адресом `https://t.me/proxy?…`, которого для схемы
  `tg://webproxy` не существует.

- **Смена `PROXY_PORT` не переносила правила zapret2 и SYN-лимитера.** Гео-блокировка
  переезжала на новый порт, а фиксы оставались висеть на старом: новый порт был без
  защиты, а на старом продолжала работать десинхронизация. Мешал ещё и стартовый
  скрипт службы zapret2 — он держит порт у себя и перетирал правила при перезапуске,
  поэтому теперь переписывается вместе с конфигом.

### Изменено

- **PQ nginx собирается со `stream`, `ssl_preread` и `stream_realip`.** Без них
  разводить трафик по SNI нечем. У workflow сборки появился параметр `build_rev`,
  чтобы пересобрать те же версии с новыми ключами и не столкнуться тегом с уже
  опубликованным релизом.

## v1.5.10 — 24.08.2026

### Исправлено

- **Телеграм-бот и панель показывали данные менеджера вместо данных цели (реаниматор).** В боте SNI приходил от настроек менеджера — тот самый домен по умолчанию, который в реаниматоре ни на что не влияет, — список пользователей был пуст, а трафик нулевой; в терминале то же самое читалось верно. Виновата песочница их служб: `ProtectHome=true` и `PrivateTmp=true` подменяют юниту `/root`, `/home` и `/tmp` пустыми каталогами, и эту подмену наследует `sudo`, которым бот и панель зовут MTProxyL. Конфиг чужого прокси лежит чаще всего именно там — рядом с `docker-compose.yml` в домашнем каталоге, — и для служб он выглядел несуществующим. Обе песочницы сняты: файловую систему бот и панель видят ту же, что и терминал. Юнит бота переписывается при `mtproxyl update`, юнит панели — её установщиком, так что обновление чинит уже поставленное.

  Заодно MTProxyL перестал подставлять своё вместо чужого: в реаниматоре SNI берётся только из конфига цели, и если прочитать его не вышло, `status --json` отдаёт пустое поле, а меню и `mtproxyl status` пишут «— конфиг цели недоступен» вместо чужого домена.

## v1.5.8 — 23.08.2026

### Новое

- **Период проверки доступности задаётся из терминала.** `mtproxyl availability interval <минуты>`, от 1 до 1440. Значение зашито в юнит `mtproxyl-availability.timer`, поэтому команда сразу переписывает его и показывает, во что новый период обойдётся по кредитам Globalping. Без аргумента показывает текущий период и время следующей проверки. Период принимает и `mtproxyl availability on <минуты>` — включить и задать за один раз.

  ```
  mtproxyl availability interval        текущий период и следующая проверка
  mtproxyl availability interval 30     проверять раз в 30 минут
  mtproxyl availability on 30           включить сразу с периодом
  ```

- **Параметры вне каталога в режиме эксперта.** У telemt есть секции-таблицы, ключи которых заранее не перечислить — их задаёт сам пользователь, и каталог такие пары описать не может. Раньше `expert set` отказывался их принимать, а вписанные в `expert.conf` руками они попадали в конфиг с ошибкой: ключ с точкой TOML читает как путь до вложенной таблицы, и `a.b = x` превращалось в `[a] b = x` вместо ключа `a.b`. Теперь такие ключи записываются в кавычках, а для их установки есть `mtproxyl expert set --raw <секция> <ключ> <значение>`. Значение при этом не проверяется, сверяется только форма записи; в остальном пара живёт как обычный override — видна в `expert list`, снимается через `expert clear`.

### Исправлено

- **Панель не показывала выбранный для бота SOCKS5** ([#34](https://github.com/Liafanx/MTProxyL/issues/34)). В v1.5.6 настройка начала применяться, но обратно в форму не возвращалась: после перезагрузки страницы поле снова выглядело пустым, с подсказкой `socks5://127.0.0.1:1080` вместо сохранённого адреса. Причина была не в панели — `mtproxyl tgbot status --json` не отдавал ключ `proxy` вовсе, а панель, даже получив его, отбрасывала при разборе. Теперь адрес доходит до формы; токен по-прежнему наружу не отдаётся, только признак, что он задан. Нужна панель 1.0.15.

- **`geoblock reapply` сообщал о неудаче, хотя правила применялись** ([#39](https://github.com/Liafanx/MTProxyL/issues/39)). Проверка состояния читала `iptables-save` через конвейер в `grep -q`. Найдя совпадение, `grep` закрывается первым, `iptables-save` получает SIGPIPE — и при включённом `pipefail` статусом всего конвейера становится 141, то есть «правил нет». Срабатывало это тем вернее, чем больше ruleset: пока остаток вывода помещался в буфер конвейера, ответ был верным, а на большом наборе правил — нет. Отсюда и то, что подряд идущие `mtproxyl geoblock` отвечали по-разному на одном и том же состоянии. Теперь дамп разбирается из переменной, а не из конвейера.

  Заодно `reapply` перестал молча глотать ошибки: он считает применённые страны и показывает «применена: N из M», отдельно называет те, для которых не скачался список IP, и ругается только когда не применилась ни одна. Правила и наборы `ipset` создаются с ожиданием блокировки xtables — её на том же сервере держат zapret2 и SYN-лимитер движка.

- **Контейнер в нескольких сетях Docker опознавался по неверному адресу** ([#40](https://github.com/Liafanx/MTProxyL/pull/40)). Адрес контейнера брался первым попавшимся из `docker inspect`. Первой в списке легко оказывается overlay- или macvlan-сеть, в которую с хоста маршрута нет, и CLI получал таймаут, не попробовав второй, рабочий адрес из bridge-сети: ссылки, статистика пользователей и доступность дата-центров оставались пустыми с диагнозом «API не отвечает». Теперь перебираются все адреса контейнера с живой пробой `/v1/health` — берётся тот, который ответил. Спасибо [@tonytkachenko](https://github.com/tonytkachenko) за находку и правку.

  По тому же адресу правились ещё две вещи. Свежий docker печатает в шаблоне пустой `IPAddress` как строку `invalid IP` — у сети `host` и у неназначенных endpoint'ов; она уходила в запросы как будто это адрес. И правила Zapret2 в режиме bridge/precise сужались до одного адреса контейнера, то есть промахивались мимо сети, через которую он реально ходит — теперь в них попадают все его адреса.

## v1.5.9 — 24.08.2026

### Исправлено

- **`expert apply` рапортовал «Hot-reload отправлен», даже когда параметр требует перезапуска.** `SIGHUP` подхватывает только часть настроек telemt — какие именно, показывает колонка «Hot-Reload» в каталоге (`expert list --catalog`). `censorship.tls_domains`, например, помечен как не hot-reloadable, а параметры вне каталога через `expert set --raw` каталогу вообще не известны. Конфиг на диске обновлялся, а работающий процесс оставался со старым значением, и команда об этом не предупреждала. Теперь `expert set` и `expert apply` проверяют все активные override и, если среди них есть хоть один без hot-reload, честно говорят об этом и просят `mtproxyl restart` вместо того, чтобы рапортовать успех.

## v1.5.7 — 23.08.2026

### Исправлено

- **`stats reset orphans` в режиме Reanimator стирал статистику целиком** ([#38](https://github.com/Liafanx/MTProxyL/issues/38)). Список живых пользователей читался из секции `users`, а в конфиге цели она называется `[access.users]` — секции с коротким именем там нет вовсе. Список выходил пустым, поэтому «удалёнными» считались все: `mtproxyl stats` показывал 12 живых пользователей как удалённых, а сброс сносил и трафик, и историю IP-адресов подчистую. Та же кнопка есть в панели. Заодно перестало теряться число убранных записей: `grep -c` при нуле совпадений печатает `0` и выходит с кодом 1, из-за чего `|| echo 0` дописывал второй ноль и арифметика падала на `syntax error in expression`. Спасибо [@Roger639](https://github.com/Roger639) за разбор.

- **Терминальные команды не проходили авторизацию на API движка** ([#37](https://github.com/Liafanx/MTProxyL/pull/37)). Когда в конфиге цели задан `[server.api] auth_header`, движок ждёт это значение в заголовке `Authorization`. Панель его слала, а CLI — нет, и получал `401`: ссылки, статистика пользователей и доступность дата-центров молча оставались пустыми. Теперь заголовок берётся из конфига цели, а отказ в авторизации диагностика называет своим именем вместо «API не отвечает». Спасибо [@tonytkachenko](https://github.com/tonytkachenko) за правку.

## v1.5.6 — 22.08.2026

### Новое

- **Сброс накопленной статистики** ([#32](https://github.com/Liafanx/MTProxyL/issues/32)). Раздел «Логи и трафик» → «Сбросить накопленное», в панели — карточка на странице «Трафик». Сбрасывается всё сразу, только счётчики трафика, только история адресов, только данные удалённых пользователей или один пользователь по метке. Настройки, секреты и сами пользователи не затрагиваются. Спасибо [@MatveyFilippov](https://github.com/MatveyFilippov) за предложение.

  ```
  mtproxyl stats                  что накоплено
  mtproxyl stats reset all
  mtproxyl stats reset traffic | ips | orphans
  mtproxyl stats reset user <метка>
  ```

- **Версия движка в панели.** Страница «Обновление» → «Версия движка»: список опубликованных релизов telemt, установка любого из них и откат на версию, которая уже лежит на диске. У бинарного движка откат идёт без сети — предыдущий бинарник хранится рядом с текущим. В терминале появились `mtproxyl engine versions` и `mtproxyl engine rollback <версия>`, откат больше не требует диалога.

- **Выбор цепочки NFT для Zapret2.** «Настройки Zapret2» → «Цепочка NFT»: `авто`, `хост` или `forward`. Раньше цепочка `forward` включалась только когда MTProxyL сам опознал цель в Docker bridge; с чужим клиентом прокси в контейнере опознания не происходило, и правила уходили в цепочки хоста мимо трафика. То же значение доступно как параметр `ZAPRET2_HOOK`.

- **`mtproxyl panel update`.** Обновление панели без вопроса «ставить поверх?». Прежняя `panel install` работает как раньше.

- **Стоимость WARP по процессору — в меню и в статусе.** В вариантах A и C шифрует не ядро, а `warpscout` в пользовательском пространстве, и через него идёт весь трафик прокси. Замер на Xeon E5-2699 v4: 100 МБ за 2,8 с (300 Мбит/с) стоили 3,8 с процессорного времени — 1,35 ядра; тот же файл напрямую — 0,55 с и 0,26 с CPU. Теперь это написано в описании вариантов, а `mtproxyl warp status` показывает, сколько процессора съел туннель.

### Исправлено

- **Временные файлы копились в `/tmp` и никогда не удалялись** ([#33](https://github.com/Liafanx/MTProxyL/issues/33)). `_mktemp` всегда вызывается через `$( )`, то есть в субшелле, и запись в список на удаление умирала вместе с ним — очистка по `trap EXIT` не удаляла ничего. Заметнее всего это было на проверке доступности: два файла на каждую проверку, около 5 МБ в сутки. Теперь в имени файла лежит PID, и уборка идёт по нему; заодно подчищаются файлы старше суток, оставшиеся от прошлых версий. Спасибо [@Roger639](https://github.com/Roger639) за разбор.

- **Прокси для телеграм-бота не применялся из панели** ([#34](https://github.com/Liafanx/MTProxyL/issues/34)). Во-первых, `proxy` — единственная настройка без точки в имени, и под шаблон sudoers она не подходила. Во-вторых, сессию к Telegram бот создаёт на старте: без перезапуска новый адрес оставался только в файле. Перезапуск теперь делает сама команда, а не меню. Спасибо [@muradurm](https://github.com/muradurm) за находку.

- **Панель после `mtproxyl panel install` показывала старую версию.** Установщик заканчивал `systemctl start`, а служба уже работала — новый бинарник лежал на диске, но старый процесс продолжал держать прежний inode. Теперь `restart`.

- **Конфиг чужого telemt в Docker не находился, если каталог был подключён не туда, где мы его ждали** ([#36](https://github.com/Liafanx/MTProxyL/issues/36)). Перебираются все точки монтирования контейнера, а не заранее известный список путей. Спасибо [@artxamer](https://github.com/artxamer) за правку.

- **После включения WARP предлагалось проверить `mtproxyl dc`**, хотя вариант C выключает middle proxy и писателей к дата-центрам в этом режиме нет. Подсказка стала зависеть от состояния ME.

## v1.5.5 — 22.08.2026

### Новое

- **Блокировка IP адресов.** Новый раздел: главное меню → «Безопасность и маршрутизация» → «Блокировка IP адресов», в панели — одноимённый пункт бокового меню. Адреса и подсети из списка не доходят до сервера: правила применяются в nftables, работают в обоих режимах и не зависят от конфига движка.

  Принимаются IPv4 и IPv6, отдельные адреса и подсети любой маски. Действие выбирается: `drop` — молча отбрасывать пакеты, `reject` — отвечать отказом ICMP. Правила поднимаются службой `mtproxyl-block` при старте, поэтому переживают перезагрузку.

  Список хранится файлом `/opt/mtproxyl/ipblock.list` и допускает комментарии:

  ```
  #сканеры
  1.1.1.1/32
  2.2.2.0/24
  #клиент
  3.3.3.3
  ```

  Комментарии сохраняются при выгрузке и загрузке. Строки, которые не являются адресом, не применяются, но и не пропадают — статус показывает, сколько их.

- **Счётчик срабатываний по каждому адресу.** Сколько пакетов и байт отбито, когда сработало впервые и когда в последний раз. Счётчики nftables обнуляются при перезагрузке, поэтому таймер раз в пять минут копит дельты в файл — накопленное не теряется.

- **Перенос списка между серверами.** `mtproxyl block export > list.txt` и `mtproxyl block import list.txt [replace|append]`; в панели — кнопки «Выгрузить файл» и «Загрузить список». При добавлении к текущему дубликаты пропускаются.

- **Аргументы установки `--block`, `--block-file` и `--block-action`.** Список блокировок ставится сразу вместе с прокси: `--block 1.1.1.1/32,2.2.2.0/24` или `--block-file /root/list.txt`, действие по умолчанию `drop`. В генераторе аргументов появился пункт «Список блокировок» — включается и выключается, как остальные.

### Исправлено

- Адрес без маски не проходил проверку формата: `1.1.1.1/32` принимался, а `3.3.3.3` — нет.

## v1.5.4 — 19.08.2026

Вместе с панелью **v1.0.12**.

### Новое

- **Движок можно держать бинарником, без Docker.** На свежей машине установка Docker занимает минуты и оставляет после себя демон, реестр образов и сотни мегабайт — ради одного процесса telemt. Теперь в мастере установки менеджера, сразу после выбора режима, спрашивается носитель движка: **Docker-образ** (по умолчанию, как раньше) или **бинарник MTProxyL-Telemt**. Во втором случае Docker не ставится вовсе.

  Бинарник берётся из релизов [telemt](https://github.com/telemt/telemt/releases): архитектура и libc определяются сами (`x86_64`, `x86_64-v3`, `aarch64`; `gnu` или `musl`), контрольная сумма sha256 сверяется, версия по умолчанию последняя — но можно выбрать любую из списка. Живёт всё в своей папке: `/opt/mtproxyl/engine/mtproxyl-telemt`, конфиг `/opt/mtproxyl/mtproxy/telemt.toml`, служба `mtproxyl-telemt.service`. Имя не `telemt` намеренно: так собственный движок менеджера не путается с оригинальной установкой telemt, которую чинит режим Reanimator.

  Всё остальное работает одинаково: меню, настройки, секреты, лимиты пользователей, режим эксперта и супер эксперта, Zapret2 и SYN-лимитер, Selfmask, WARP, гео-блокировка, бэкапы, веб-панель и телеграм-бот. Запуск, остановка, перезапуск и горячая перезагрузка конфига идут через systemd, логи — из журнала юнита.

- **Смена движка на работающей установке.** Главное меню → «Движок» → «Перейти на бинарник» либо «Перейти на Docker-образ»; из командной строки — `mtproxyl engine backend binary|docker`. Порт, секреты и настройки сохраняются, конфиг перегенерируется под новое имя, прежний носитель убирается. При уходе на бинарник предлагается удалить образы движка — сам Docker остаётся в системе. Веб-панель получает права на журнал новой службы, чтобы логи движка в ней не замолчали.

- **Аргументы `--engine docker|binary` и `--engine-version <тег>`.** Установка аргументами и корневой установщик умеют ставить менеджер сразу на бинарнике: `bash install.sh -- --mode manager --engine binary --engine-version 3.4.25 …`. При переустановке поверх (`--force`) без `--engine` носитель остаётся прежним. `--cpus` и `--memory` с бинарником не принимаются: это лимиты контейнера, у службы их задают средствами systemd.

- **Переезд по SSH и «Перенос аргументами» знают про носитель.** `mtproxyl migrate` поднимает на новой машине движок тем же способом и той же версии, что работает на старой. В генераторе команды появился пункт «Движок»: можно оставить как здесь, взять бинарник той же версии или последней — и, например, переехать с контейнера на бинарник заодно с переездом.

- **Панель показывает носитель движка.** Раздел «Режим работы» → карточка «Движок»: контейнер или бинарник, состояние, конфиг и порт. Диалог перехода в Reanimator с бинарником предлагает снять или остановить службу, а не удалить контейнер, которого нет.

- **Лимиты CPU и памяти работают у обоих движков.** `--cpus` и `--memory` (и те же вопросы в мастере) у контейнера остаются лимитами docker, а у бинарника превращаются в `CPUQuota` и `MemoryMax` его службы: одно ядро — 100%, `512m` — `MemoryMax=512M`.

- **Обновление и откат версии для бинарника.** `mtproxyl engine update <тег>` перекачивает и перезапускает службу, `mtproxyl engine rollback` возвращает предыдущую версию с диска — она лежит рядом как `mtproxyl-telemt.prev`, поэтому откат не требует сети. `mtproxyl engine rebuild` у бинарника перекачивает текущую версию заново.

### Исправлено

- **Upstream-маршруты могли пропасть из конфига движка.** Конфиг собирается из списка маршрутов в памяти, а часть команд его не загружала: `sni-policy`, Selfmask, установка аргументами. Такая команда пересобирала конфиг без единого `[[upstreams]]` — вместе с подразумеваемым маршрутом `direct`. Со стороны это выглядело так: после установки аргументами маршрутов в конфиге нет, добавляешь один — появляются два, а перезапуск прокси «внезапно» всё чинит. Теперь генератор конфига догружает маршруты сам, если их ещё не читали.

- **Экран «Доступность дата-центров» первую минуту после запуска движка сообщал, что middle proxy выключен.** Пока telemt поднимает пул писателей, его API отдаёт `middle_proxy_enabled: false`, и MTProxyL принимал это за настройку. Теперь ответ сверяется с конфигом: если ME там включён, показывается «ещё поднимается», а не «выключен». То же и в уведомлениях бота.

- **Панель на голом IP предлагала выпустить Let's Encrypt.** Сертификаты на IP-адрес не выдаются, и certbot честно отказывал — но уже после того, как его установили и спросили почту. Проверка домена пропускала IPv4 как валидный. Теперь по IP предложения нет вовсе, а `mtproxyl panel cert <IP>` отказывает сразу и объясняет почему.

## v1.5.2 — 19.08.2026

Вместе с панелью **v1.0.11**. Переезд на другой сервер, установка аргументами без вопросов и разбор жалоб по WARP.

### Новое

- **Установка аргументами, без единого вопроса.** `mtproxyl install --mode manager --port … --secret … --selfmask …` ставит менеджер целиком: порт, домен ссылок, FakeTLS SNI, секреты, рекламная метка, маскировка, SNI-политика, лимиты контейнера, Zapret2 или SYN-лимитер, оптимизация By-MEKO и Selfmask. Те же аргументы принимает и корневой установщик после `--`: `bash install.sh -- --mode manager --port 443 …`. Мастер никуда не делся — без аргументов всё как раньше. Полный список: `mtproxyl install --help`.

  Реаниматор аргументами не ставится намеренно: у чужой цели свой конфиг, порт и движок, и задавать их со стороны нечем.

- **Переезд на другой сервер: `mtproxyl migrate root@новый.сервер`.** Прокси блокируют по адресу, и лечится это только сменой машины; бэкап с восстановлением работает, но занимает время. Теперь MTProxyL читает свои же настройки и поднимает на новой машине копию: тот же порт, домен ссылок, SNI, секреты **с лимитами, квотами, сроками и заметками**, метка, маскировка, SNI-политика, Zapret2 или SYN-лимитер, By-MEKO, Selfmask. Панель переезжает вместе с `config.toml` — логин, пароль и `jwt_secret` прежние, мастер настройки на новой машине не запускается; бот ставится с прежним токеном и админами. Про панель и бота переезд спрашивает, по умолчанию да; ответить заранее — `--panel`/`--no-panel`, `--tgbot`/`--no-tgbot`. В конце предлагается удалить старую копию — по умолчанию нет. Есть `--dry-run`: показывает, что поедет, и не трогает ничего. Из меню — «Обновления и бэкапы → Переезд на другой сервер».

  Вход только по ключу: пароль MTProxyL не спрашивает и не хранит. Если ключа на той стороне нет, предлагается `ssh-copy-id` — пароль вводите вы. A-запись домена переводит владелец: этого за него не сделает никто.

  **A-запись сверяется до начала работ.** Сертификат Let's Encrypt выпускается в момент установки, и проверка домена уходит туда, куда запись смотрит сейчас: пока она на старом сервере, на новом не поднимутся ни Selfmask, ни HTTPS панели. Переезд узнаёт адрес новой машины, сравнивает с записями Selfmask, панели и домена ссылок, называет, куда они ведут сейчас, и переспрашивает — вместо того чтобы выяснить это уже посреди установки. С самоподписанным сертификатом A-запись не нужна вовсе, и предупреждения нет.

  **Лимиты CPU и памяти контейнера не переносятся.** Их подбирали под старую машину: на машине с меньшим числом ядер docker отказывался запускать контейнер («range of CPUs is from 0.01 to 1.00, as there are only 1 CPUs available») — прокси не поднимался, а переезд шёл дальше как ни в чём не бывало. Теперь лимиты остаются свободными, а после установки проверяется, что контейнер действительно работает, и о неудаче говорится прямо.

- **Доступность дата-центров Telegram из меню.** Команда `mtproxyl dc` была, а пункта не было. Теперь «Дополнения (утилиты) → Дата-центры Telegram»: та же таблица с RTT, писателями и покрытием, и порог предупреждения рядом.

- **SNI-политика расширена до всех четырёх значений** ([#31](https://github.com/Liafanx/MTProxyL/issues/31)). В меню менеджера предлагались только `mask` и `drop`, хотя движок понимает ещё `accept` и `reject_handshake`, а командой `mtproxyl sni-policy` они и раньше ставились. Теперь оба есть и в «Безопасность и маршрутизация → SNI-политика», и в настройках. Нужны, когда за mask-бэкендом стоит свой веб-сервер или Nginx Proxy Manager с чужими доменами.

- **Файл подкачки на маленькой машине.** На сервере с гигабайтом памяти и без подкачки docker, движок и особенно сборка панели упираются в OOM: ядро убивает процесс, а установка выглядит зависшей. Теперь при памяти 1 ГБ или меньше и отсутствующей подкачке предлагается создать файл на 1 ГБ — по умолчанию да. Работает и в мастере, и при установке аргументами, а значит и при переезде. Отдельно: `mtproxyl swap status|on [МБ]|off`.

- **«Перенос аргументами» в меню.** «Обновление, бэкапы и миграция» → пункт собирает из текущей конфигурации готовую команду установки для другой машины: скопировали, вставили, выполнили. Нужен там, где переезд по SSH не проходит — до нового сервера может не быть доступа отсюда. Любой пункт включается, выключается и правится, значения по умолчанию берутся из конфига. Адрес в ссылках попадает в команду, только если это домен: литеральный IP привязан к старой машине.

- **Аргумент `--geoip yes|no`** — поставить базу GeoIP при установке аргументами: страна, город и ASN в истории IP.

- **`mtproxyl selfmask panel-cert`** — отдать веб-панели текущий сертификат Selfmask. Нужно после переустановки панели: свой сертификат она делает самоподписанным, и её адрес снова становится голым IP вместо домена. Переезд зовёт это сам, когда Selfmask на новой машине поднялся.

### Исправлено

- **Установка обрывалась на 404, если install.sh брали из одной ветки, а файлы качались из другой.** Список библиотек зашит в сам установщик, и на ветке без нового файла загрузка падала с невнятным «Не удалось скачать». Теперь 404 распознаётся отдельно: MTProxyL называет ветку и подсказывает указать её явно через `--branch`.

- **Установка аргументами вставала на вопросах, которые задавал не мастер.** Ответы были заготовлены только для верхнего уровня, а вложенные подтверждения — оптимизация By-MEKO, правка окна wscale — спрашивали сами и ждали ввода, которого не будет. Теперь в неинтерактивном режиме любое приглашение сразу берёт своё значение по умолчанию, а «нажмите любую клавишу» пропускается: заготавливать ответ под каждый вопрос по отдельности больше не нужно.

- **Переустановка аргументами поверх существующей уводила порты метрик и API в один и тот же.** Оба подбирались независимо «первым свободным», а прежние порты в этот момент держал ещё не пересозданный контейнер — обоим доставался один номер, и установка обрывалась на «порт API совпадает с портом прокси или метрик». Теперь у существующей установки прежние порты берутся как есть, а подбор учитывает уже выбранный.

- **Отказ Let's Encrypt всегда объяснялся одинаково — «проверьте DNS и порт 80».** Вывод certbot выбрасывался, и настоящая причина терялась. Теперь он разбирается: при превышении лимита на выпуск MTProxyL так и говорит, называет время следующей попытки и предлагает пока поднять Selfmask с самоподписанным сертификатом; в остальных случаях показывает последние строки ответа certbot.

- **Почта для Let's Encrypt была обязательной по факту.** При установке аргументами без `--selfmask-email` подставлялся выдуманный `admin@<домен>`, а certbot не принимает пустое `-m`. Теперь почта необязательна: без неё регистрация идёт анонимно, и не приходят только письма об истечении.

- **`fake_cert_len` при Selfmask не определялся никогда.** Длину сертификата мерили, подключаясь к своему же домену на 443, — а там отвечает сам прокси, а не nginx Selfmask, и замер всегда проваливался: в настройках оставалось значение по умолчанию 2048 вместо настоящего. Теперь длина берётся из выписанного сертификата на диске: у Let's Encrypt это обычно ~900 байт, и разница видна снаружи.

- **Оптимизация окна wscale предлагалась с ответом «нет» по умолчанию.** Zapret2 дробит ClientHello, и окно поближе к пределу работает лучше, но согласиться надо было вручную. Теперь по умолчанию «да», а при установке аргументами применяется без вопроса.

- **Переезд не вёз конфиг режима супер эксперта.** Свой `config.toml` предлагалось перекладывать руками. Теперь он едет вместе с остальным, и режим включается на новой машине. Выключить его там можно в любой момент: файл не удаляется, а MTProxyL возвращается к своему конфигу, собранному из перенесённых настроек.

- **Переезд зависал на установке бота, когда с нового сервера не видно Telegram.** С сервера в РФ доступа к `api.telegram.org` часто нет, бот там всё равно не заработает, а установка молча тянулась минутами. Теперь доступность проверяется заранее и бот пропускается с объяснением; сама установка ограничена по времени.

- **Вопросы про панель и бота проскакивали без ответа.** Если пароль для `ssh-copy-id` вводили не с первого раза, лишние переводы строки оставались в буфере терминала и отвечали за пользователя на ближайшие вопросы. Перед ними буфер теперь очищается.

- **Панель не могла включить вариант C WARP: «sudo: a password is required».** В правах sudo, которые панель выписывает себе при установке, не было строки `warp on upstream` — вариант C появился в 1.5.1, а список команд остался прежним. Переустановка панели не помогала: файл генерировался тем же установщиком. Права обновятся сами при `mtproxyl panel install` или обновлении панели.

- **`mtproxyl warp location DE` всегда отвечала ошибкой.** Введённое значение проверялось не по нему самому, а по уже сохранённому: на пустой настройке разбор возвращал пустоту, и любая локация — хоть `DE`, хоть `DE,FRA` — отвергалась как некорректная. Задать локацию из меню было невозможно вовсе.

- **Панель на самоподписанном сертификате сама лезла в Let's Encrypt, когда её ставили не с клавиатуры.** Предложение «выпустить сертификат сейчас?» по умолчанию отвечает «да», а при запуске без терминала ответа не приходит вовсе — установка молча уходила к certbot и упиралась в чужую A-запись. Теперь без терминала предложение не показывается: печатается, как выпустить сертификат потом.

- **Установка аргументами донашивала лимиты контейнера из прежней установки.** При `--force` поверх старой копии `PROXY_CPUS` и `PROXY_MEMORY` брались из неё, даже если в аргументах их не было, — и на машине с меньшим числом ядер docker отказывался запускать контейнер. Теперь лимиты берутся ровно из аргументов, а `--cpus` сверяется с числом ядер до начала работ: раньше об этом сообщал сам docker, уже после установки.

- **Переезд ругался «integer expression expected» при осмотре нового сервера.** Занятость порта считалась через `grep -c`, а он печатает `0` и выходит с кодом 1 — запасное `|| echo 0` дописывало второй ноль, и сравнение падало на `0\n0`. На ход переезда это не влияло, но в лог сыпалась ошибка.

- **Переезд говорил, что не смог перенести `secrets.conf`, хотя перенёс.** Файл клался и прокси перезапускался одной командой, и неудачный перезапуск — например, когда контейнер не поднялся по своей причине — объявлял непереехавшими уже разложенные секреты. Теперь это два разных шага с разными сообщениями.

- **Адрес сервера определялся как IPv6, и ссылка не открывалась.** Перебор сервисов шёл через `||`, а сервис, ответивший пустотой с кодом 0, обрывал перебор: адрес оставался пустым либо приходил IPv6, и в `tg://proxy?server=…` уезжал голый IPv6-литерал. Теперь сначала спрашиваем IPv4 (`curl -4`) и проверяем сам ответ, а не код возврата; если наружу не достучались — берём свой глобальный IPv4 мимо docker-мостов; IPv6 остаётся последним вариантом, когда IPv4 нет вовсе.

- **Переезд спотыкался о сменившийся ключ хоста.** Если на новом сервере переустановили систему, его SSH-ключ меняется, и `ssh-copy-id` падал с «REMOTE HOST IDENTIFICATION HAS CHANGED» — переезд заканчивался стеной предупреждений про MITM. Теперь MTProxyL проверяет это первым делом, показывает отпечаток, который сервер отдаёт сейчас, объясняет, что так бывает после переустановки и точно так же выглядит подмена, и только с явного согласия забывает старый ключ (`ssh-keygen -R`). Заодно `ssh-copy-id` получает те же параметры подключения, что и остальные вызовы, — со своими умолчаниями он спотыкался там, где обычное подключение уже проходило.

- **Неверный токен бота устанавливался молча.** Проверка токена ходила в Telegram с `curl -f`, и ответ «Unauthorized» был неотличим от недоступной сети: мастер писал «проверить не вышло, продолжаем» и ставил бота, который никогда не заработает. Теперь ответ с ошибкой разбирается и называется своими словами, а недоступная сеть по-прежнему установку не блокирует.

- **Адрес панели с IPv6 печатался нерабочей ссылкой** — адрес склеивался с портом без скобок (`https://2a0a:…:::8080`).

- **Найденные туннели добавлялись масками, а не именами** ([#30](https://github.com/Liafanx/MTProxyL/issues/30)). Установка Zapret2 находила на сервере `awg0` и записывала мимо очереди весь набор `awg* wg* tun*` — вместе с интерфейсами, которых ещё нет. Теперь в список попадает ровно то, что нашлось. Прежнее поведение осталось под ключевым словом `std` в меню, а новое `auto` находит текущие туннели заново.

## v1.5.0 — 16.08.2026

Вместе с панелью **v1.0.9**.

### Новое

- **Маршрут до Telegram через Cloudflare WARP.** Для серверов, с которых серверы Telegram недоступны. В туннель уходит не весь трафик, а только подсети Telegram: клиенты приходят на прокси по-прежнему напрямую. Правила живут в ядре, поэтому работает во всех трёх режимах — свой telemt, чужая цель реаниматора и посторонний прокси в «только оптимизации». Эндпоинты Cloudflare ищет [warpscout](https://github.com/vernette/warpscout): он поднимает настоящий туннель к каждому кандидату и смотрит, где тот выходит. Бинарник берётся из релиза оригинального проекта, а если тот недоступен или не понимает нужные ключи — из нашей сборки в релизах MTProxyL (её собирает отдельный workflow из форка).

  Вариантов два, оба в меню «Безопасность и маршрутизация → Telegram через WARP», в панели и в `mtproxyl warp`:

  **A — SOCKS5 warpscout + redsocks.** Туннель поднимает сам warpscout в пользовательском пространстве, ядро ни при чём. Умеет обфускацию (`awg`, `masque`) — проходит там, где обычный WireGuard режут по сигнатуре рукопожатия. Подводные камни: туннель один, без запасного узла — после обрыва службу поднимает systemd и заново ищет эндпоинт; в тракте лишний процесс redsocks; заворачивается только TCP.

  **B — интерфейс WireGuard + policy routing.** Обычный wg-туннель в ядре, маршрут выбирается по метке. Переподключается сам, лишних процессов нет. Подводные камни: только чистый WireGuard, и нужен модуль ядра.

  **C — socks5-upstream в конфиге движка.** Правил в ядре нет вовсе: warpscout поднимает SOCKS5, а telemt ходит через него своей записью `[[upstreams]]`. Самый простой путь, когда движок наш: в режиме менеджера MTProxyL прописывает маршрут сам, у чужой цели реаниматора поднимает туннель и печатает, что дописать в её конфиг (`mtproxyl warp hint`), подставляя адрес шлюза, если цель в docker bridge. Подводные камни: через socks уходит весь исходящий трафик движка, включая загрузку TLS-метаданных с локального mask-бэкенда — её MTProxyL возвращает на прямой маршрут отдельной областью (`censorship.tls_fetch_scope`), иначе маскировка не поднимает сертификат. Свои маршруты без области MTProxyL предлагает выключить и включает обратно при `warp off`: движок раскладывает трафик между всеми такими маршрутами по весу, и часть соединений шла бы мимо туннеля.

  Где выходить — на выбор: по умолчанию живой эндпоинт с наименьшей задержкой, иначе коды стран (`DE,NL`) или узлов Cloudflare по коду аэропорта (`FRA,AMS`). Подсети Telegram берутся из официального списка `core.telegram.org/resources/cidr.txt` со встроенным запасным. Что маршрут работает, видно по двум вещам: Cloudflare подтверждает `warp=on`, а счётчик nft показывает, сколько пакетов до Telegram ушло в туннель.

  **Middle proxy с WARP несовместим, и MTProxyL это проверяет до включения.** Ключи ME-рукопожатия обе стороны выводят из адреса и порта, с которых прокси пришёл к Telegram, а выход WARP меняет и то, и другое от соединения к соединению. Проверено тремя способами: с ME покрытие падает до нуля; подстановка `middle_proxy_nat_ip` не помогает; конфигурация по мануалу движка (`direct`-upstream с `bind_addresses` на адрес туннеля и отдельная таблица маршрутов, при которой STUN-рефлексия становится bind-aware) тоже не поднимает писателей — за несколько минут рефлексия увидела три разных выходных адреса Cloudflare. Для ME нужен выход с постоянным соответствием «адрес:порт» — свой сервер с публичным адресом, а не общий CGNAT. Поэтому включение отказывается работать при `use_middle_proxy = true` и предлагает перевести движок на прямую маршрутизацию (в менеджере — сам, в реаниматоре — покажет, что поправить). Вместе с ME перестаёт действовать рекламная метка: там, где Telegram недоступен, она всё равно не работала.

- **Порог доступности дата-центров настраивается и выключается.** По нему телеграм-бот решает, писать ли о просадке связи с Telegram, и по нему же панель красит строки таблицы DC. Раньше он менялся только командой `mtproxyl dc threshold N`, а теперь ещё и в меню «Телеграм бот» → «Уведомления» пунктом «Порог покрытия дата-центров», и в панели прямо в карточке DC на дашборде. Ноль (он же `mtproxyl dc threshold off`) выключает предупреждения целиком: таблица и цифры остаются, но «просело» больше никто не говорит — ни бот, ни панель. Порог живёт в настройках MTProxyL, а не в конфиге бота: два независимых значения расходились бы, и панель показывала бы тревогу тогда, когда бот молчит.

### Исправлено

- **Панель показывала выдуманный период автопроверки доступности.** На странице «Доступность из России» стояло «проверка идёт сама раз в 15 минут» — зашитым текстом, независимо от `AVAILABILITY_INTERVAL`. Теперь период, число зондов и время следующей проверки приходят от CLI и показываются как есть; если автопроверка включена, а systemd-таймер не поднялся, панель об этом прямо говорит, а не рисует расписание, которого нет. Заодно «Проверить сейчас» перестала прятать остаток квоты Globalping: после проверки страница перечитывает состояние, а не берёт его из ответа, где квоты нет.

Пункт «Импорт секретов» читал восемь полей — формат экспорта из соседнего пункта меню, — а файл базы секретов (его отдаёт «сохранить секреты перед удалением») хранит десять: в нём есть момент создания и рекламная метка. Поля разъезжались на одно, и пользователю с лимитом в 2 IP доставалась квота в 2 байта, то есть мгновенная блокировка. ## v1.4.9 — 15.08.2026

Вместе с панелью **v1.0.8**.

### Новое

- **Обновление кода бота показывает, что происходит.** Вместо одной строки «обновляем телеграм-бота», висевшей всё время, идёт разбор по шагам: какие файлы приехали и какие не изменились, обновляется ли venv, переписываются ли права sudo, поднялась ли служба (а если нет — хвост журнала). Заодно закрыт разрыв: раньше обновление кода не трогало venv вовсе, и новая зависимость приехала бы файлом, но не установилась — теперь при изменившемся `requirements.txt` зависимости доставляются, а при неизменном venv не трогается, чтобы не платить минутой pip за каждое обновление.

- **Телеграм-бот умеет ходить через локальный SOCKS5.** Нужно там, где серверы Telegram с хоста недоступны напрямую: бот идёт к ним через прокси, который вы подняли сами — MTProxyL его не ставит и за ним не следит. Настройка в меню «Телеграм бот» пунктом «Прокси для Telegram», в панели — карточкой на странице бота, из CLI — `mtproxyl tgbot set proxy socks5://127.0.0.1:1080` (`off` возвращает прямой ход). Принимается только `socks5://[логин:пароль@]хост:порт`: схему проверяют и bash, и панель, потому что иначе опечатка всплыла бы падением службы при старте. Схему `socks5` в aiogram поддерживает отдельный пакет `aiohttp-socks` — он добавлен в зависимости бота и приезжает с обновлением его кода; если venv старый, бот скажет об этом в журнале и не станет молча ходить напрямую.

- **Доступность дата-центров Telegram.** Новая проверка отвечает на вопрос, обратный «доступности из РФ»: не доходят ли до нас пользователи, а доходим ли мы до Telegram. Данные берутся из REST API движка (`/v1/stats/dcs`) — в Prometheus разбивки по DC нет вовсе. `mtproxyl dc` показывает таблицу: DC, RTT, писатели (живых / нужно) и покрытие; `mtproxyl dc status --json` — то же машинно, `mtproxyl dc threshold N` меняет порог. Та же таблица приехала на дашборд панели сразу после ошибочных соединений и в телеграм-бот командой `/dc`. При падении общего покрытия ниже порога (по умолчанию 80%) бот шлёт уведомление и второе — когда связь восстановилась; уведомление отключается там же, где остальные. Покрытие считается по всем DC разом — живые писатели к нужным, а не среднее по столбцу: у DC 4 писателей десять, у остальных три.

- **Реаниматор: цель больше не перезапускается зря** ([#26](https://github.com/Liafanx/MTProxyL/issues/26)). telemt следит за своим конфигом и применяет пользователей на ходу, а MTProxyL после каждой правки перезапускал службу — то есть добавление одного пользователя из панели рвало соединения всем клиентам. Теперь перед перезапуском состав и лимиты включённых пользователей сверяются с тем, что отдаёт API цели: сошлось — перезапуск пропускается, не сошлось или API не отвечает — работает прежняя ветка с рестартом. Проверено на добавлении, удалении, включении, выключении и лимитах: PID и число соединений не меняются. Касается меню, панели и телеграм-бота разом — все они ходят одной командой. Спасибо @Roger639 за замеры и разбор.

- **Режим «только оптимизация»** ([#23](https://github.com/Liafanx/MTProxyL/issues/23)). Для тех, у кого прокси свой — другая реализация MTProto или вовсе другой сервис. MTProxyL работает как набор host-фиксов (zapret2, SYN-лимитер, оптимизация By-MEKO, гео-блокировка, дополнения) и больше не ведёт себя так, будто движок обязан быть: не жалуется на ненайденный telemt, не спрашивает про конфиг и порт и не показывает домен-заглушку вместо вашего. Пункты про пользователей, ссылки и статистику из меню уходят — брать их неоткуда. Предлагается при установке реаниматора, когда telemt не нашёлся, включается и выключается в «Цель / режим»; в `mode --json` появилось поле `tools_only`.

- **Zapret2: правила можно сузить до своего трафика.** Три настройки в меню «Настройки zapret2» и в панели, раздел «Лимитер и защита»:

  **Основной порт** — раньше он всегда брался из конфига прокси. Теперь его можно задать вручную: клиенты приходят на другой порт при пробросе, балансировщике или своём DNAT. Пусто — снова из конфига.

  **Фильтр по IP** — в правила добавляются `ip saddr`/`ip daddr`, и очередь получает только трафик нашего адреса, а не всё, что идёт через тот же порт. Включён по умолчанию, адрес определяется при установке по таблице маршрутов: за NAT в пакетах стоит частный адрес сервера, и подставить публичный значило бы не поймать ни одного пакета. Принимается только IPv4 — домен в правило nft не встанет и уронит применение всей таблицы.

  **Мимо очереди** — список интерфейсов, чей трафик проходит без обработки (`awg* wg* tun*`). Когда рядом с прокси работает VPN, туннель несёт чужой HTTPS на том же 443, и десинк ломает его вместе с нашим: сайты открываются через раз, Telegram в туннеле не подключается. Установка сама находит такие интерфейсы на сервере и предлагает их исключить. Спасибо @TeslA1402 за разбор и PR.

- **Панель можно выключить, не удаляя.** `mtproxyl panel disable` останавливает службу и снимает её с автозапуска, `mtproxyl panel enable` возвращает обратно; то же кнопкой в меню **Дополнения → Веб-панель**. Бинарник, конфиг, пароль и сертификаты остаются на месте — раньше единственным способом убрать панель с глаз было удаление, после которого её ставили и настраивали заново. В строке состояния выключенная панель теперь так и подписана, отдельно от «установлена, не запущена»: снятая с автозапуска служба не вернётся и после перезагрузки.

- **Показываются все рабочие ссылки, а не одна.** Движок принимает те виды, что включены в `[general.modes]`: с выключенной маскировкой это и `dd` (secure), и `ee` (TLS) — ровно так telemt и пишет при запуске. Раньше меню и `secret link` строили ровно одну ссылку и половина рабочих подключений оставалась не показанной. Теперь их видно все — в меню «Ссылки на прокси», после `secret add`, `rotate` и `clone`, в выводе `secret link` и `secret qr`, в конце установки и в телеграм-боте; QR рисуется на первую. У чужой цели ссылки берутся прямо из её API, поэтому список совпадает с журналом telemt.

- **Уникальные IP видны везде.** Сколько разных адресов сейчас подключено — в главном меню рядом с соединениями, в меню «Логи и трафик» общим числом и напротив каждого пользователя, в `status --json` и `traffic --json` полем `unique_ips`, в панели на странице «Трафик» отдельной колонкой и в карточке «Всего», в телеграм-боте на экране статуса. Раньше это число было только у режима реаниматора: уникальные адреса считает REST API движка, а менеджер брал статистику из Prometheus, где такой метрики нет.

### Исправлено

- **Панель: правка параметров zapret2 включала Smart By-MEKO.** Кнопка «Сохранить и применить» выбирала действие по сохранённому `NFT_MODE`, а не по тому, что изменили. При `NFT_MODE=smart` правка любого параметра zapret2 запускала лимитер, и тот по своей же взаимоисключающей логике останавливал zapret2. Теперь переприменяется та подсистема, к которой относятся изменённые параметры; если задеты обе — та, что защищает сейчас, а выключенная молча не включается.

- **Цель в Docker bridge: API считался недоступным.** У контейнера своя петля, и `listen = "127.0.0.1:9091"` внутри него с хоста не виден — MTProxyL честно стучался на 127.0.0.1 и получал отказ, а сообщение «API не отвечает» ничего не объясняло. Теперь для цели в bridge адрес подбирается сам: сначала проверяется опубликованный порт на 127.0.0.1, затем берётся адрес контейнера. Если API привязан к петле контейнера, диагностика так и пишет и показывает, что поправить в конфиге цели — `listen = "0.0.0.0:9091"` и `whitelist` с сетью docker, без которого движок отклоняет запросы уже после подключения. Установка панели в этом режиме подсказывает тот же адрес.

- **Панель не передавала рекламную метку пользователя** ([#28](https://github.com/Liafanx/MTProxyL/issues/28)). Поле в форме было, но при создании и при правке уходили только метка-имя, секрет и лимиты. Оказалось, что метки на пользователя не было и в самом MTProxyL: он умел только общую из `[general]`. Теперь она есть — `mtproxyl secret adtag <метка> <32 hex|remove>`, пункт «Рекламная метка» в меню пользователей и поле в карточке пользователя в панели. Пишется в `[access.user_ad_tags]` и перекрывает общую только для этого пользователя; в реаниматоре — в конфиг цели, движок подхватывает на ходу. Пустое поле снимает метку.

- **Телеграм-бот, режим менеджера: трафик показывался нулевым.** Бот читал из статуса поле `traffic_total`, а менеджер отдавал только `traffic_in` и `traffic_out`. Теперь `status --json` в обоих режимах отдаёт `traffic_total`, а бот в режиме менеджера дополнительно показывает разбивку по направлениям.
- **Телеграм-бот: меню оставалось над файлом бэкапа.** Архив уходил в чат последним сообщением, а меню правилось на месте — и оказывалось выше. Теперь после отправки архива, в том числе автобэкапом наблюдателя, меню пересоздаётся внизу.

## v1.4.7 — 11.08.2026

Отзывы и просьбы пользователей: обновление MTProxyL приходит в панель и ставится оттуда же. Вместе с панелью **v1.0.6**.

### Новое

- **Обновление MTProxyL из панели.** Раньше о вышедшей версии узнавал только тот, кто заходил в меню по ssh: проверка и установка жили в CLI и там же заканчивались. Теперь на дашборде появляется строка «Вышла версия X», а на странице «Обновление» — раздел «Версия MTProxyL» с текущей и опубликованной версией, ссылкой на заметки о релизе и кнопкой. Обновление идёт фоном, с тем же журналом, что и остальные долгие операции: видно, какой шаг выполняется, и виден итог по каждой библиотеке. Обновляется сам скрипт и его библиотеки — настройки, секреты и работающий прокси не затрагиваются; панель тоже не трогается, у неё своё обновление рядом.

Недоступный github не считается ошибкой команды: установленная версия всё равно известна, о неудаче говорит поле `error`. Установка из ветки сравнивается с этой же веткой, а не с релизами.

### Документация

- **Клиент за домашним роутером с `nfqws` не подключается.** Разобран случай, когда прокси здоров, а не работает у кого-то одного: на его роутере (Keenetic, OpenWrt, Padavan) стоит свой обход на том же `nfqws`, который собирает ClientHello ради SNI, — а zapret2 намеренно шлёт его рваным и с битой контрольной суммой. Лечится на роутере: параметром `--reasm-disable=tls_client_hello` либо внесением домена маскировки в исключения `nfqws`. Описано в README и в [zapret2.md](zapret2.md).

### Исправления

- **Установка панели не умела обойти занятый порт 80, хотя выпуск сертификата отдельным пунктом умел.** Собственный ACME панели требует порт 80 и при старте, и при каждом продлении, а установщик занятый порт мог только назвать: «освободите и повторите». В итоге выбравший Let's Encrypt получал панель без сертификата. Теперь после установки и переустановки MTProxyL проверяет, чем всё кончилось, и предлагает выпуск тем же способом, что и пункт «Выпустить сертификат»: если порт держит заглушка Selfmask, проверка домена идёт через её webroot, иначе держатели порта останавливаются на несколько секунд и возвращаются обратно. Осознанно выбранный самоподписанный сертификат не трогается — вопрос задаётся, только если домен называли при установке. Заодно установщик перестал требовать email (он необязателен с v1.4.5, но здесь всё ещё обрывал установку) и перестал терять MTProxyL при запуске не от root: каталог `/opt/mtproxyl` закрыт от посторонних, и проверка «есть ли скрипт» врала — вместе с ней отключалась и вся интеграция.
- **История IP пополнялась, только пока открыта панель.** Адреса записывались в момент запроса списка пользователей — то есть при открытой вкладке; закрыл браузер, и всё, что подключалось до следующего захода, терялось. Отсюда и ощущение, что в истории видны лишь «активные» и те, кто подключился только что: движок держит списки адресов недолго и на длинную память не рассчитан. Теперь снимки делает systemd-таймер `mtproxyl-ip-history.timer` — раз в 5 минут, независимо от панели и меню. Управление — в меню **«Логи и трафик» → «История IP»**: состояние, время следующего снимка, интервал, глубина хранения и снимок по кнопке; пункт есть в обоих режимах и открывается даже при остановленном движке (раньше остановленный движок закрывал весь экран трафика). То же снаружи: настройка `IP_HISTORY_INTERVAL` (в минутах, `0` — выключить) в CLI и в разделе «Обслуживание» панели, вручную — `mtproxyl ip-history status|flush|on|off`. Снимок стоит около 0,1 с процессорного времени: один запрос к API движка и одно слияние базы, без сборки полного списка пользователей. У обновившихся таймер ставится сам при первом запуске MTProxyL — установщик к тому моменту уже отработал, а больше поставить его некому.
- **Обновление скачивалось в `/tmp`, а ставилось в `/opt/mtproxyl`.** Если это разные файловые системы (а `/tmp` часто tmpfs), перенос выполняется копированием поверх — то есть перезаписывает файл, который в этот момент читает работающий bash. Теперь загрузка идёт рядом с целью, и замена всегда остаётся атомарным переименованием.
- **Права sudo у панели именные, и новая команда через них не проходила.** Список в `/etc/sudoers.d` перечисляет подкоманды поимённо, а обновление панели её же кнопкой меняет только бинарник — файл прав остаётся прежним. Отказ теперь объясняется по-русски и с готовым решением: `mtproxyl panel install`. Панель новее самого MTProxyL распознаётся отдельно и просит обновить его один раз из терминала, а не показывает ошибку разбора вывода.

Уменьшение подрезает историю на ближайшем обновлении списка пользователей.
- **Автопроверку доступности можно выключить.** Проверка по расписанию тратит квоту Globalping и обращается к прокси, а нужна не всем: на странице «Доступность из России» появился переключатель, состояние продублировано на дашборде. Выключенная автопроверка не отменяет кнопку «Проверить сейчас» — проверять руками можно всегда. По умолчанию включена; выбор переживает перезапуск панели и не сбрасывается при сохранении цели проверки.
- **Сводка доступности на дашборде.** Процент, сколько зондов из скольких ответило и когда была последняя проверка — рядом со статусом движка, со ссылкой на подробную страницу. Раздел «Доступность из России» появился в v1.4.4, но на дашборд не выводился.

### Исправления

- **Zapret2 не запускался в LXC-контейнерах.** В сгенерированном `mtproto.conf` не было `--uid`, и `nfqws2` сбрасывал привилегии под своё значение по умолчанию — внутри unprivileged LXC это давало `setgroups: Invalid argument`, служба не поднималась, и установка откатывалась сама. Причина не в id-mapping контейнера: `nobody`/`nogroup` на месте и корректны. Теперь в конфиг явно пишется `--uid=65534:65534` (`nobody:nogroup`), а значения вынесены в настройки `ZAPRET2_UID`/`ZAPRET2_GID` — их видно в шапке меню Zapret2 и можно поменять пунктом **[12]**, если в системе другой непривилегированный пользователь. Спасибо за подробный разбор с проверкой id-mapping.
- **Панель молча прятала настройки, которых не знала.** Страница настроек раскладывала ключи по жёстким группам, а всё, чего в них нет, не показывала вовсе — из-за этого новый `IP_HISTORY_LIMIT` в панели не появился, хотя CLI его уже отдавал. Незнакомые ключи теперь выводятся отдельным блоком «Прочее»: настройка, добавленная в MTProxyL, больше не пропадёт из панели молча.
- **Проверка домена на PQ без указания домена упиралась в connection refused.** Пустое поле подставляет текущий SNI-домен, но порт при этом брался 443 — а прокси слушает свой. Теперь подставляется и порт прокси; явно указанный `домен:порт` работает как раньше.
- **Определение IP сервера отдавало домен вместо адреса.** `get_public_ip` первым делом возвращает `CUSTOM_IP` — «IP/домен сервера» из настроек ссылок, а туда часто вписывают домен. Дальше это значение шло в сверку с A-записью, и мастер Selfmask сообщал о несовпадении всегда, даже когда домен указывал ровно на этот сервер. Тем же болели привязка NFT к IP при установке (предупреждала «нужен IPv4» и тут же снова брала домен) и пункт «определить автоматически» в меню лимитера. Теперь в этих местах адрес спрашивается у сети.
- **Проверка A-записи сверяла только один адрес.** Домен с несколькими A-записями и сервер с несколькими адресами считались несовпадением. Теперь сверяются все записи домена со всеми адресами сервера, а когда домен за CDN и совпадения быть не должно — об этом сказано прямо, а не как об ошибке.
- **Сертификат для панели требовал email.** Let's Encrypt регистрирует аккаунт и без него, но `panel cert` отказывался продолжать. Пустой email теперь допустим — выпуск идёт с `--register-unsafely-without-email`, теряются только письма о скором истечении (продление всё равно автоматическое).
- **После выпуска сертификата установщик показывал IP вместо домена** и добавлял «браузер предупредит о недоверенном сертификате» — хотя сертификат настоящий. Сводка знала только про `acme_domain`, а `panel cert` переводит панель на файлы сертификата, и имя остаётся только внутри него: теперь оно оттуда и читается. Заодно при переходе на выпущенный сертификат из конфига убирается `self_signed` — флаг оставался и врал про недоверенный сертификат всем, кто по нему судит.
- **Настройки самого MTProxyL были недоступны в реаниматоре — с двух сторон сразу.** `settings set` целиком закрывался проверкой режима, хотя часть настроек к конфигу движка отношения не имеет; а в панели они жили на странице «Настройки прокси», которая в реаниматоре скрыта вся. Теперь `IP_HISTORY_LIMIT` и `BACKUP_RETENTION_DAYS` меняются и в реаниматоре, и при включённом супер эксперте — чужой конфиг они не трогают, — а в панели переехали в новый раздел **«Обслуживание»**. Глубина истории IP работает в обоих режимах; хранение бэкапов показывается только в Manager, потому что бэкапить чужую цель нечем.
- **Убраны две настройки, которые ничего не делали.** `AUTO_UPDATE_ENABLED` и `SECRET_AUTO_ROTATE_DAYS` не читала ни одна строка кода: ни таймера, ни cron, ни проверки при запуске — автообновление MTProxyL и ротация секретов по расписанию просто не были реализованы, а переключатели в меню и панели обещали обратное. Ротация секретов по-прежнему доступна вручную: `mtproxyl secret rotate <метка>`. Значения в `settings.conf` остаются лежать и ничего не ломают.

## v1.4.4 — 08.08.2026

Сбор жалоб с реальных установок: нагрузка на CPU от вкладки «Пользователи» в обоих режимах, невозможность закрыть окно лога в панели, проверка PQ на системном OpenSSL, возврат fake SNI после Selfmask, `CUSTOM_IP` без эффекта, права на `settings.conf`, запуск без ручного `sudo`. Плюс два новых умения панели: проверка доступности прокси из России глазами зондов и выпуск сертификата Let's Encrypt при занятом 80 порте. Вместе с панелью **v1.0.3**.

### Новое

- **Проверка доступности прокси из России** — новый раздел панели «Доступность из России». Панель просит публичную сеть зондов Globalping выполнить HTTPS-рукопожатие с портом прокси с российских резидентских (eyeball) сетей — именно там действует фильтрация по абонентам, а не с дата-центровского узла, которому сервер отвечает независимо от блокировок в стране. Успех — полученный TLS-сертификат (то же рукопожатие, что делает клиент Telegram), а не просто открывшийся TCP-порт: так ловится и случай, когда порт отвечает, но сессия обрывается на рукопожатии. Проверка не требует прав root и ничего не ставит на сервер — обычные исходящие запросы к Globalping API. Раз в 15 минут проверка идёт сама, результат виден индикатором на дашборде.
- **Цель проверки доступности можно задать руками** — форма «Что проверять» на той же странице: адрес, порт и fake SNI. Автоопределение (домен заглушки, привязанный адрес, внешний IP) верно для обычной установки и слепо там, где адрес знает только оператор: прокси за CDN, второй домен на том же сервере, проброшенный порт. Пустое поле означает «определить самому», и в подсказке стоит то, что подставится. Выбор переживает перезапуск панели.
- **Учёт часовой квоты Globalping.** Сервис отпускает 250 кредитов в час (500 с бесплатным токеном), один зонд — один кредит. Панель считает потраченное сама скользящим часом и отказывает в проверке, которая в остаток не влезает, — до обращения к сервису, а не по факту 429, когда квота уже потрачена и следующие проверки тоже обречены. Плановая проверка при этом просто пропускается с записью в лог, прошлый вердикт остаётся в силе. Остаток кредитов и время их возврата показаны на странице.
- **Панель можно поставить только для локального доступа.** Установщик отдельно спрашивает, куда привязывать сокет: как раньше на все интерфейсы или на `127.0.0.1`. Во втором случае порт снаружи не слушается вовсе — нет ни открытой формы входа, ни того, что можно брутфорсить; ходят в такую панель через ssh-туннель (`ssh -L 8080:127.0.0.1:8080 …`), команду установщик печатает после установки. Про шифрование он в этом режиме не спрашивает и оставляет HTTP: ssh шифрует канал сам, а по петле трафик машину не покидает — самоподписанный сертификат добавил бы только предупреждение браузера на каждый вход. `mtproxyl panel cert` для такой панели предупредит, что выпускать сертификат незачем.
- **`mtproxyl panel cert [домен] [email]`** — выпуск сертификата Let's Encrypt для веб-панели, с учётом занятого 80 порта. Если работает заглушка Selfmask, проверка домена проходит через её же webroot и никого останавливать не нужно; иначе держатели порта 80 останавливаются ровно на время выпуска и запускаются обратно. Дальше сертификат передаётся панели копией файлов, а `acme_domain` из её конфига снимается — свой ACME панели больше не нужен. Пункт **[6]** в меню панели.

### Исправления

- **Zapret2 пропускал мимо себя закрытие соединений.** Разгрузка держалась на том, что уже обработанное соединение помечается в conntrack и дальше идёт мимо очереди, — но под это правило попадали и пакеты FIN. Не увидев закрытия, `nfqws2` оставлял соединение в своём состоянии живым. За NAT, тем более CGNAT, это оборачивалось разрывами: клиент порт не выбирает, трансляция берёт его из небольшого пула и переиспользует сразу после закрытия, которое отследила по FIN, — и для `nfqws2` новое подключение выглядело как SYN внутри «ещё установленного» соединения, обрабатываясь по устаревшему состоянию. Теперь мимо очереди проходят только пакеты с данными: `tcp flags & (fin | syn | rst | ack) == ack`. FIN, SYN и RST снова доходят до `nfqws2` — на объём трафика это не влияет, их единицы на соединение. Правило поменялось в обоих местах, где строится таблица: при установке и в скрипте службы.
- **Проверка `wscale` только советовала, но ничего не чинила.** При большом TCP-буфере `2^wscale` уходит за 1400 байт, и дробление ClientHello становится невозможным ни при каком `win ACK` — проверка печатала пример команд и оставляла пользователя с нерабочим обходом. Теперь она предлагает применить оптимизацию: `/etc/sysctl.d/99-mtproxyl-wscale.conf` с четырьмя параметрами (`rmem_max`, `wmem_max`, `tcp_rmem`, `tcp_wmem`) по 16 МБ даёт `wscale = 9`, после чего `win ACK` подбирается сам (2 — окно 1024 байта). После применения перепроверяются все четыре значения — сверка по двум пропускала случай, когда чужой файл перебивает только `wmem`. Если их перетирает другой файл — а `/etc/sysctl.conf` читается последним всегда, и переименованием нашего это не обойти, — MTProxyL называет такие файлы и предлагает закомментировать в них конфликтующие строки, оставив рядом копию. Если отказаться, буфер всё равно выставляется на ходу, но с прямым предупреждением: до перезагрузки. Предложение появляется при установке, переустановке и в диагностике; включённая оптимизация видна в шапке меню Zapret2, снимается вместе с zapret2.
- **Ядро на той же ситуации отвечало ACK вместо нового соединения.** Даже когда `nfqws2` состояние почистил, у ядра оставался сокет в TIME_WAIT, и SYN с только что освободившегося кортежа не открывал новое подключение — клиент висел до таймаута. Установка и перезапуск zapret2 теперь выставляют `net.ipv4.tcp_tw_reuse = 1` (файл в `/etc/sysctl.d`, чтобы пережить перезагрузку, плюс применение на месте). Что именно выставлено и каким было прежнее значение, видно в логе установки и в итоговой сводке «Что было сделано»; если значение задаёт другой файл `sysctl.d`, он называется поимённо. Удаление zapret2 возвращает прежнее значение. Полное удаление MTProxyL заодно убирает все свои файлы в `/etc/sysctl.d` — раньше настройки ядра оставались на машине после удаления.
- **Список пользователей грузил CPU до полки.** На каждого пользователя команда заново ходила в API цели и перезаписывала базу трафика (`flush_target_traffic_to_disk` внутри `get_persistent_target_user_stats`), четырежды разбирала конфиг цели ради лимитов, отдельно перечитывала базу IP и звала `json_escape` в командной подстановке. Замер на стенде: **24 пользователя — 12.0 сек** на один вызов, а панель просит этот список каждые 10 секунд, то есть ядро было занято непрерывно. Теперь всё общее собирается один раз на весь список: **0.18 сек на 120 пользователей**, вывод команды не изменился. Аналогично разгружен `traffic --json` цели (1.36 → 0.24 сек). Замеры сделаны на стенде в режиме реаниматора.
- **Слияние истории IP занимало десятки секунд процессорного времени — в обоих режимах.** Чтобы вытеснить самый старый адрес, на каждый новый IP дважды перебиралась вся база целиком. При заполненной истории (200 адресов × 120 пользователей) один флаш — **40 сек CPU**; он выполняется на каждом запросе списка пользователей. Функция слияния общая, поэтому доставалось и `relay_stats/user_ips_db` у менеджера, и `relay_stats/target_user_ips_db` у реаниматора. Переписано на один проход `awk` с вытеснением через `sort`: **0.12 сек**, правила те же (первое появление адреса сохраняется, вытесняется тот, кого дольше всех не видели). История IP теперь приходит отсортированной — свежие адреса первыми.
- **`traffic --json` в режиме менеджера собирал всё общее на каждого пользователя.** `is_proxy_running` (настоящий `docker inspect`), таблица метрик движка, база трафика и снимок сессии читались внутри цикла по секретам. Теперь всё это берётся один раз на весь список, в цикле остаётся арифметика — как и в ветке реаниматора. Список пользователей менеджера разгружен раньше, в v1.4.2 и v1.4.3.
- **Разбор ответа API цели запускал по пять `sed` на каждого пользователя.** Статистика и списки IP разбирались чанками с отдельным подпроцессом на каждое поле — полторы сотни процессов на 30 пользователей за один запрос. Разбор тот же, но в одном `awk`.
- **Окно с логом операции в панели нельзя было закрыть** — оно возвращалось даже после перезагрузки страницы. Слот операции один на всю панель и хранит последний результат до следующего запуска, поэтому у блока появился крестик, а закрытие подтверждается на сервере. Идущую операцию закрыть нельзя — её вывод единственное, что говорит, что сервер ещё работает.
- **Проверка SNI-домена на постквантовый обмен ключами отказывалась работать на системном OpenSSL 3.5+.** Пункты 12.1/12.2 спрашивали только про свою сборку и писали «PQ OpenSSL не установлен», хотя пункт 12.3 в том же меню отвечал, что она не нужна — системного достаточно. Заодно исправлен сам вердикт: с OpenSSL 3.5 `s_client` печатает не `Peer Temp Key`, а `Negotiated TLS1.3 group`, из-за чего маркер X25519 не определялся вовсе и проверка всегда показывала «Маркер: НЕТ». Установка своей сборки (12.3) больше не отказывает из-за системного nginx: nginx нужен заглушке, а openssl — проверке, и это разные пакеты.
- **Отключение Selfmask не возвращало прежний fake SNI**, хотя предупреждение это обещало: домен заглушки затирал `PROXY_DOMAIN` без следа. Теперь перед включением снимается снимок (fake SNI, backend маскировки, `unknown_sni_action`, длина поддельного сертификата), и отключение возвращает его. В реаниматоре так же возвращается конфиг цели — раньше в нём оставался наш домен вместе с `mask_host = 127.0.0.1`, то есть цель продолжала ходить на уже выключенную заглушку. Панель в предупреждении называет домен, который вернётся.
- **`CUSTOM_IP` не влиял на ссылки движка.** Смена адреса сохраняла настройку, но не перегенерировала конфиг движка, а IP-литерал вообще не попадал в `[general.links] public_host` — «движок определит сам». Смысл настройки ровно обратный: её задают там, где автоопределение промахивается (NAT, несколько адресов). Теперь заданный IPv4 или домен пишется в конфиг, а конфиг перечитывается сразу.
- **`/opt/mtproxyl/settings.conf` читается всеми.** Порт, fake SNI и домен видно снаружи по одному подключению, секретов в файле нет — но забрать их скриптом можно было только из-под root, и каждая перезапись настроек отбирала права заново. Каталог остаётся закрытым на листинг (711), соседние `secrets.conf`/`detect.conf` доступнее не стали, а `relay_stats` и `backups` закрыты явно.
- **Алиас `mtproxyl` → `sudo mtproxyl`** для тех, кто заходит на сервер обычным пользователем: установщик кладёт его в `/etc/profile.d/mtproxyl.sh` и в `~/.bashrc`/`~/.zshrc` того, кто запустил установку. Под root алиас не определяется — условие проверяется при запуске шелла, а не при установке.
- **Панель не опрашивает сервер, пока её вкладка скрыта.** Панель обычно висит открытой сутками, и каждый опрос — это запуск CLI на сервере. При возвращении на вкладку данные обновляются сразу.
- **`mtproxyl panel install` с ветки ставил панель из релиза.** Обёртка сперва пробовала последний релиз и переходила к сборке из исходников, только если релиза нет вовсе, — а он есть почти всегда. CLI, поставленный с `dev`, после установки получал панель, собранную с `main`, без правок своей ветки: установка не падала, просто ставила не то. Теперь на не-`main` ветке панель сразу собирается из её же исходников. Собрать панель с произвольной ветки можно и через GitHub Actions — у workflow сборки появился ручной запуск, бинарники прикладываются к прогону артефактом.
- **Меню панели показывало адрес прокси вместо адреса самой панели.** При `listen = 0.0.0.0` адрес брался из `get_public_ip`, а та первым делом отдаёт `CUSTOM_IP` — «IP/домен сервера» из настроек прокси, то есть хост для `tg://`-ссылок. ## v1.4.0 — 04.08.2026

Главное в релизе — веб-панель **MTProxyL-Panel**: опциональный интерфейс ко всему, что умеет MTProxyL, работающий в обоих режимах. CLI и меню остаются основным способом управления и ничего не теряют.

### Веб-панель MTProxyL-Panel

- Опциональный веб-интерфейс: дашборд, пользователи, трафик, телеметрия, логи, конфигурация, переключение режимов, Selfmask, лимитер и Zapret2, блокировка стран, исходящие маршруты, бэкапы, экспертные параметры и супер эксперт. Интерфейс на русском.
- Ставится из MTProxyL — `mtproxyl panel install` или меню **Дополнения → Веб-панель**, — либо отдельным установщиком без MTProxyL. Управление: `mtproxyl panel status|restart|uninstall`.
- HTTPS по умолчанию: при установке выпускается самоподписанный сертификат, поддерживается свой сертификат и Let's Encrypt по домену.
- Панель работает под собственным непривилегированным пользователем `mtproxyl-panel`. Для команд, которым нужен root, установщик создаёт `/etc/sudoers.d/mtproxyl-panel-mtproxyl` — список **конкретных** разрешённых подкоманд, а не право запускать `mtproxyl` целиком. При отключении интеграции или удалении панели файл убирается.
- Долгие операции (переключение режима, Selfmask, восстановление из бэкапа, установка) идут в фоне с живым выводом команды на экране, а не безмолвным спиннером: по нему видно текущий шаг и отличим медленный шаг от зависшего.
- Панель замечает, что опрашивает движок другого режима: URL API задаётся один раз при установке, а переключение Manager ⇄ Reanimator меняет, какой движок главный — иначе на дашборде молча показывались бы чужие пользователи и трафик.
- Панель выпускается отдельными релизами с тегом `mtproxyl-panel-vX.Y.Z`. Пока релиза нет, собирается прямо из ветки — в Docker, без установки тулчейна на сервер.

За основу взята **[telemt_panel](https://github.com/amirotin/telemt_panel)**: оттуда перенесено ядро — авторизация, обновление бинарника, потоковые логи через WebSocket, GeoIP-поиск и редактор TOML. Всё, что относится к самому MTProxyL — режимы, пользователи, Selfmask, лимитер, маршруты, бэкапы — надстроено поверх, интерфейс переведён на русский.

### Пользователи: накопленный трафик и история IP

- У каждого пользователя хранится **история подключённых IP**: раз увиденный адрес остаётся в ней и после того, как списки движка «активные»/«недавние» опустели. Движок помнит только текущую сессию и обнуляет её при перезапуске, поэтому история копится MTProxyL на диске, с отметками первого и последнего появления адреса.
- Рядом с сессионным трафиком показывается **накопленный за всё время** — он переживает перезапуск движка и цели.
- И то и другое работает одинаково в режиме менеджера и реаниматора: у цели своя база, отдельная от менеджерской, иначе после смены режима числа чужого движка сложились бы со своими.
- В панели: колонка «Накоплено» с сортировкой в списке пользователей, а в карточке — метрика и отдельный раздел «История IP» с временем первого и последнего подключения каждого адреса. История сортируется по любой колонке — по адресу, стране или датам; открывается по последнему подключению, от свежих.

### GeoIP

- Опциональная база GeoIP ставится одной командой — `mtproxyl geoip install` — или кнопкой в разделе **Дополнения** веб-панели. Доступно в обоих режимах: база лежит в общесистемном `/var/lib/GeoIP/`, а не в конфиге прокси.
- С ней рядом с адресами пользователей появляются страна, город и провайдер (ASN); без неё всё работает по-прежнему, просто без геоданных.
- Источник — зеркало [P3TERX/GeoLite.mmdb](https://github.com/P3TERX/GeoLite.mmdb) (данные MaxMind GeoLite2, CC BY-SA 4.0). Ставятся City и ASN; ASN не обязательна — без неё не определяется только провайдер.
- Если база уже установлена системным пакетом или `geoipupdate`, она подхватывается сама. Поставленная из панели замечается сразу — перезапускать её не нужно.
- `mtproxyl geoip status|remove` — проверить и удалить.

### Reanimator

- **Пользователями цели можно управлять.** Раздел был закрыт целиком: и список, и добавление отвечали «нет владения конфигом/движком цели». Теперь все операции читают и пишут `[access.users]` конфига цели — как это делал бы руками её администратор. Набор подкоманд совпадает с менеджерским, поэтому одинаково работают и CLI, и панель.
- Выключённый пользователь остаётся в файле закомментированным: движок такую строку не читает, ключ не теряется и возвращается той же командой. Удаление и переименование ведут пользователя по всем секциям, где он упоминается — лимиты соединений, уникальных IP, квота и срок.
- Пользователи цели появились и в интерактивном меню — отдельным пунктом.
- **Конфиг цели правится целиком и построчно.** Читается и пишется он через MTProxyL от root: файл принадлежит самой цели (у systemd-установки `telemt:telemt` в каталоге 750), а панель работает непривилегированной. Перед записью делается резервная копия и проверка, что текст всё ещё похож на конфиг telemt; владелец и права сохраняются от исходного файла. Форма быстрых настроек меняет только те строки, которые правит, — чужой файл не перекраивается: отступы, порядок секций и хвостовые комментарии остаются как были.
- **Накопление трафика у цели.** Счётчики цели обнуляются при её перезапуске, а перезапускает её кто-то другой и когда угодно — без своей базы «всего» означало бы «с последнего рестарта». Первый опрос и смена источника данных дают нулевую дельту с установкой точки отсчёта: иначе чужие терабайты, накопленные до подключения, записались бы себе.
- Трафик удалённых пользователей виден отдельной помеченной строкой: он был израсходован и остаётся в итоге, поэтому сумма по пользователям сходится с «всего».

- Явное включение REST API движка и белые списки для API и метрик — по мануалу движка.

### CLI

Почти все команды требуют root — раньше без sudo команда либо падала на конкретной операции с неочевидной ошибкой (Docker, nft, чтение `/opt/mtproxyl`), либо через `check_root` с понятной, но пользователю всё равно приходилось самому вспоминать добавить sudo и перезапускать. Теперь `mtproxyl` ведёт себя как `sudo mtproxyl` без этого шага; поверх настоящего sudo это ничего не меняет — панель, как и раньше, вызывает CLI уже от root.

Установка это делала, включение Smart-режима — тоже, а запуск существующего экземпляра не делал ничего: правила лимитера и `nfqws2` оставались работать вместе на одном трафике. - После настройки selfmask MTProxyL ждёт не просто ответа API цели, а появления в нём ссылок: telemt поднимает API раньше, чем заполняет `[general.links]`, и сразу после перезапуска выводилось «IPv4-ссылки не найдены в ответе API цели».

### Установка telemt из режима Reanimator

- Если на сервере не найдено ни процесса, ни службы, ни бинарника telemt, MTProxyL предлагает поставить оригинальный telemt — запускается официальный установщик проекта (`telemt/telemt`, `install.sh`) как есть, со своими вопросами про язык, порт и TLS-домен. Конфликтом считается только чужой процесс, контейнер (в том числе собственный контейнер MTProxyL) или telemt, запущенный мимо systemd.

При обновлении конфиг цели не перезаписывается целиком — меняются только порт и `tls_domain`, тюнинг, `[server.api]` и секреты остаются.
- В панели главного меню отсутствие цели показывается явно: «telemt на сервере не найден — чинить нечего».

### Исправления по итогам ревизии кода

- `mtproxyl expert list|set|clear` вызывали функции, которых нет в проекте, и падали с `command not found`. Команды переписаны на реальный API: значение проверяется по каталогу параметров, override сохраняется/удаляется и сразу предлагается пересборка конфига с hot-reload. Меню режима эксперта работало и раньше — ломался только CLI.

Теперь ключ ищется и меняется строго внутри своей секции, содержимое пишется обратно в тот же файл — владелец и права чужого конфига сохраняются.

Добавлены проверка фактического состояния правил (в CLI и в меню), команда `mtproxyl geoblock reapply` и пункт «Переприменить правила»; при смене порта правила переносятся автоматически.
- Установка Zapret2 сначала снимает свой уже работающий или недоустановленный экземпляр (служба, `nfqws2`, остатки прошлой попытки) и только потом проверяет, свободна ли NFQUEUE. Раньше это делалось лишь при явной переустановке, поэтому «первая» установка поверх остатков видела свою же занятую очередь 200 и молча переезжала на 250+. После сброса сразу запускается проверка wscale: `win ACK = 10` даёт реальное окно 10 × 2^wscale, и на сервере с большим TCP-буфером оно выходит за 1400 байт — дробление ClientHello перестаёт работать, поэтому корректное значение пересчитывается и предлагается к применению (как это уже делается после установки).

### Работа с целью

- После перезапуска цели MTProxyL ждёт, пока она поднимет API (до 8–10 секунд), и только потом запрашивает ссылки и статистику: раньше сразу после рестарта выводилось «API не отвечает», хотя через пару секунд всё работало. То же ожидание — при входе в главное меню сразу после установки в режиме Reanimator.
- Новые ссылки после настройки selfmask печатаются последним блоком, а не в середине вывода, где их затирали проверка selfmask и итоговая сводка.
- Если у цели выключены метрики движка, MTProxyL не просто показывает, что дописать в конфиг, а предлагает включить их сам (`metrics_listen`, `metrics_whitelist`) и перезапустить цель. Порт подбирается свободный: 9090 часто занят, и цель бы просто не поднялась. После перезапуска ждём именно метрики (они поднимаются позже API), а если цель вообще не стартовала — говорим об этом и показываем, куда смотреть.

### Ввод в меню

- Все поля ввода читаются через readline: Backspace работает независимо от того, что шлёт терминал — `^?` (0x7f) или `^H` (0x08). Раньше при `^H` в значение попадали символы `^H^H^H…` вместо удаления, и введённое нельзя было исправить.
- Настройка `erase` терминала больше не перезаписывается принудительно: если она уже задана в сессии, MTProxyL её сохраняет.
- Доступны привычные сочетания readline: Ctrl+U (очистить строку), Ctrl+W (удалить слово), Ctrl+A/Ctrl+E, стрелки влево/вправо.
- Пустой ответ (просто Enter) больше не ломает вывод: readline в этом случае завершает строку без перевода каретки, и следующая строка лога затирала приглашение прямо на экране («[i] Перезапуск telemt.service...и поднялись? [Y/n]»).

### Состояние цели в режиме Reanimator

- Процессы внутри контейнеров видны в PID namespace хоста, поэтому `telemt`, работающий в любом контейнере (в том числе в собственном контейнере менеджера), считался запущенной локальной целью — панель писала «РАБОТАЕТ» после остановки службы. Теперь учитываются только процессы хоста.
- Для цели с systemd-юнитом источник правды — сам юнит: после `systemctl stop` цель показывается остановленной. Процесс, поднятый мимо systemd, по-прежнему определяется как работающий.
- Время работы для остановленной службы больше не берётся из `ActiveEnterTimestamp` (он остаётся и после остановки); для процесса вне systemd считается по времени его жизни.
- Состояние, перезапуск, reload, логи и остановка одинаково работают для целей `local`, `config_only` и `manual` — раньше состояние определялось только для `local`.
- Остановка и SIGHUP отправляются только процессам хоста, а не всем `telemt` в системе. Если после остановки службы остался процесс вне systemd — об этом сообщается с его PID.

## v1.3.0 — 30.07.2026

### Режим Reanimator

Функционал проекта [MTproxy-reanimation](https://github.com/Liafanx/MTproxy-reanimation) перенесён в MTProxyL как второй режим работы:

- **Manager** *(по умолчанию, прежнее поведение)* — устанавливает и владеет своим telemt.
- **Reanimator** — находит уже работающую установку telemt на сервере (Docker-контейнер сторонней панели, MTProxyMax, процесс/systemd-юнит `telemt.service` либо просто конфиг-файл) и применяет к ней NFT SYN limiter, Zapret2 MTProto fix, iOS-фиксы, оптимизацию By-MEKO и точечный тюнинг — без установки движка и без перезаписи чужого конфига целиком.

Режим выбирается на первом шаге мастера установки и переключается в любой момент: `mtproxyl mode [manager|reanimator]`.

Репозиторий MTproxy-reanimation помечен как deprecated — развитие функционала происходит здесь.

#### Работа с целью

- Управление целью её же способом: `systemctl` для `telemt.service`, `docker start/stop/restart` для контейнера, `mtproxymax` для MTProxyMax. Остановленная служба тоже определяется и запускается.
- Ссылки на прокси, трафик, соединения и список пользователей берутся из API самой цели (`GET /v1/users`). Работает без Prometheus-метрик, которые в telemt по умолчанию выключены; ссылки выводятся только IPv4.
- Метрики движка используются, если цель их отдаёт (`metrics_listen`/`metrics_port`); иначе выводится готовая инструкция, что добавить в конфиг.
- Диагностика проверяет цель: способ управления, порт, конфиг, SNI-домен, API, метрики и применённые фиксы.
- Домен(SNI) в панели читается из конфига цели, а не из настроек менеджера.
- `mtproxyl edit-config` и отдельный пункт меню — правка конфига цели в `$EDITOR`/nano с резервной копией и предложением рестарта, только если файл действительно изменился.
- Тюнинг после установки применяет набор таймаутов, который MTProxyL держит в своём конфиге (`client_handshake` 90, `tg_connect` 30, `client_keepalive` 120), одним подтверждением. Произвольные параметры остаются доступны через `tune set`.
- Перед первой правкой чужого конфига делается резервная копия, путь печатается.

### Selfmask

- **Новый тип сертификата — самоподписанный.** Работает в обоих режимах, позволяет указать любой домен, в том числе несуществующий: A-запись и порт 80 не нужны, ACME и http→https redirect не создаются, системный nginx на 80 порту не трогается. Let's Encrypt остаётся вариантом по умолчанию.
- В режиме Reanimator selfmask точечно патчит `[censorship]` конфига цели (`tls_domain`, `mask_host`, `mask_port`, `unknown_sni_action`) — одно подтверждение, один рестарт, затем вывод новых ссылок.
- Настройки selfmask хранятся отдельно для каждого режима: заглушка, настроенная для менеджера, больше не отображается активной в реаниматоре и наоборот.
- Selfmask доступен из меню «Дополнения», а не только из manager-настроек.
- Формулировки про PQ переписаны: для заглушки, которую поднимает сам MTProxyL, поддержка X25519MLKEM768 гарантирована; проверка нужна только для чужого домена в `tls_domain`.

### Zapret2

- Порог в Lua завязан на значение `win SYN+ACK` и больше не расходится с ним.
- **Дополнительные порты.** Кроме порта прокси можно указать любое число портов и диапазонов (`8443,9000-9100`): в `--filter-tcp` уходит список через запятую, в NFT-правила — анонимный set.
- **Поддержка Docker bridge.** Если цель в bridge-сети, правила ставятся в цепочку `forward`, а не в `prerouting`/`postrouting` хоста. Две стратегии: `simple` — только по портам, `precise` — с сужением до IP контейнера, с ожиданием IP при загрузке и watcher'ом, который переналагает правила при смене IP. Стратегия переключается после установки.
- Переход между Zapret2 и SYN limiter в обе стороны предлагает отключить активный механизм, а не блокирует переключение.

### Интерфейс

- Пункты всех меню нумеруются подряд, только цифрами, `0` — назад/выход; буквенные сокращения убраны.
- Главное меню показывает свой набор пунктов для каждого режима: в Reanimator скрыто всё, что требует владения движком и конфигом (секреты, настройки, движок, режим эксперта, бэкапы, upstream, SNI-политика).
- Лимитер: вместо пресетов «жёсткий/средний/мягкий» один стандартный Classic (1/second burst 1) либо свои значения.
- «Дополнительные правила» → «Добавить порт для текущих правил».
- Дополнения: проверка ограничений сервера (censorcheck) и проверка PQ по реальному домену текущего режима.

### Установка и совместимость

- Поддержка AlmaLinux и других производных: определение ОС дополнено фоллбэком по `ID_LIKE`. Установка Docker на минимальных RHEL 9 образах доставляет `dnf-plugins-core`, умеет скачать `.repo` напрямую и повторяет установку с `--allowerasing`.
- `nftables` ставится и для Zapret2, а не только для SYN limiter. В зависимости добавлены `jq` и редактор.
- Порт при установке проверяется на занятость, включая вариант по умолчанию; показывается, кто именно держит порт, и предлагается другой порт либо осознанное продолжение. Несколько установок на одном сервере не запрещены.

## v1.2.0 — 27.07.2026

### Zapret2 MTProto fix

Добавлен новый режим обхода — **Zapret2 MTProto fix**.

Принципиально другой подход по сравнению с SYN limiter:
- **SYN limiter** (Smart By-MEKO / Classic) — ограничивает входящие SYN-пакеты от клиента
- **Zapret2 fix** — работает на уровне TCP-пакетов, активно запутывает анализ первого handshake

#### Как работает

1. Сервер отвечает на SYN с уменьшенным TCP window (1400 байт) → клиент вынужден дробить ClientHello
2. Сервер запоминает начальный ACK. Пустые ACK идут с `window=10` пока клиент не отправил payload
3. Когда клиент отправил первый payload — соединение отпускается через `fwmark + ct mark`
4. Первый data-пакет (ClientHello) режется на 3 части: 1-я нормально, 3-я со смещением, 2-я с **битой контрольной суммой**
5. Нельзя собрать ClientHello → пропускает соединение
6. Клиент ретрансмитирует → соединение устанавливается штатно, дальше трафик без вмешательства

#### iOS fingerprint bypass

iOS-клиенты автоматически определяются по TCP SYN fingerprint и маркируются через `fwmark` — проходят без манипуляций с окном.

#### NFT таблица

Новая структура `ip MTProtoL`:
- `predefrag` — пропуск помеченных пакетов + notrack
- `output` — ct mark set для marked пакетов
- `postrouting` — ct mark accept + queue
- `prerouting` — ct mark accept + queue

Все правила имеют `counter` для мониторинга.

#### Проверка wscale и автоподбор win ACK

Эффективность обхода зависит от TCP window scale (`wscale`), который ядро выставляет по размеру буфера:

```
Реальное окно = win_ACK × 2^wscale  →  должно быть < 1400 байт
```

Скрипт автоматически проверяет это при установке и в диагностике, при необходимости предлагает скорректировать `win ACK`.

#### При включении

Zapret2 fix **заменяет** SYN limiter — при установке лимитер автоматически отключается.

#### Управление

- Меню: `[7] NFT лимитер → [z] Zapret2 MTProto fix`
- CLI: `mtproxyl nft zapret2` / `mtproxyl nft zapret2-stop` / `mtproxyl nft zapret2-rm` / `mtproxyl nft zapret2-wscale`

#### Настраиваемые параметры

| Параметр | Умолч. | Описание |
|----------|:------:|---------|
| out-range | `a` | Диапазон исходящих пакетов (always — Lua решает сама) |
| in-range | `a` | Диапазон входящих пакетов |
| split len | `400` | Размер частей при разрезании ClientHello |
| win SYN+ACK | `1400` | TCP window в SYN+ACK |
| win ACK | `10` | TCP window в пустых ACK (подбирается по wscale) |

#### Используемый инструмент

[zapret2](https://github.com/bol-van/zapret2) — пакетный манипулятор с Lua-скриптами. Бинарники скачиваются автоматически при установке для `amd64` и `arm64`.
