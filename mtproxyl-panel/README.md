# MTProxyL-Panel

Веб-панель управления прокси на движке **telemt** с поддержкой хостовых
возможностей **MTProxyL**: переключение режимов, Selfmask, лимитер, Zapret2,
блокировка стран, маршруты и бэкапы.

Один статический бинарник: фронтенд встроен в него, отдельный веб-сервер не
нужен. Интерфейс полностью на русском.

---

## Быстрая установка

Панель ставится **после** того, как поднят прокси — ей нужен работающий telemt
с доступным API.

### Из MTProxyL (рекомендуется)

```bash
mtproxyl panel install
```

Или через меню: `mtproxyl` → **Дополнения** → **Веб-панель MTProxyL-Panel**.

Интеграция с MTProxyL включится автоматически, права sudo будут выданы только
на нужные команды.

### Отдельно

```bash
curl -fsSL https://raw.githubusercontent.com/Liafanx/MTProxyL/main/mtproxyl-panel/install.sh -o install-panel.sh
sh install-panel.sh install
```

Установщик спросит логин и пароль администратора (пароль — дважды), а
остальное определит сам и покажет на подтверждение.

Если MTProxyL установлен, адрес API берётся из конфига движка **того режима,
который сейчас активен**: у менеджера это его собственный конфиг, у
реаниматора — конфиг чужой цели, и порт там свой. Заголовок авторизации,
если он задан в конфиге движка, подставляется тоже. Перед записью конфига
установщик проверяет, что API действительно отвечает.

В режиме Manager движок работает в Docker, поэтому про путь к бинарнику и
systemd-службу установщик не спрашивает — их там нет; вместо этого он
настраивает чтение логов из контейнера.

Панель выпускается отдельно от MTProxyL, её релизы помечены тегом
`mtproxyl-panel-vX.Y.Z`. Конкретную версию можно указать явно:

```bash
sh install-panel.sh install mtproxyl-panel-v1.0.3
```

### Сборка из ветки, без релиза

Пока релиз не выпущен (или чтобы проверить свежую ветку) панель собирается
прямо из исходников:

```bash
sh install-panel.sh install --from-source=dev
```

Если на сервере есть Docker — сборка пойдёт в нём, и тулчейн на сервере не
останется. Так же MTProxyL собирает сам движок telemt. Без Docker понадобятся
Go 1.25+ и Node.js 20+. В обоих случаях нужен `git`.

`mtproxyl panel install` выбирает этот путь сам, когда CLI поставлен не с
`main`: релиз панели собран с `main` и правок вашей ветки не содержит, так что
ставить его было бы обманчиво «успешной» установкой не того кода. На `main`
ставится релиз, а сборка из исходников предлагается, только если релиза нет.

Порт установщик спрашивает, по умолчанию 8080 — после установки панель
доступна на `https://<адрес сервера>:8080`.

### Только с локальной машины

Установщик отдельно спрашивает, куда привязывать сокет:

- **со всех интерфейсов** (по умолчанию) — панель открыта из интернета;
- **только с этой машины** — `listen = "127.0.0.1:<порт>"`, снаружи порт не
  слушается вовсе.

Второй вариант закрывает панель от интернета целиком: снаружи не видно ни
порта, ни формы входа, то есть брутфорсить нечего. Ходят в такую панель через
ssh-туннель:

```bash
ssh -L 8080:127.0.0.1:8080 <пользователь>@<адрес сервера>
```

и открывают `http://127.0.0.1:8080` у себя в браузере.

Про шифрование в этом режиме установщик не спрашивает и оставляет HTTP: до
браузера соединение идёт внутри ssh, а по петле трафик машину не покидает —
самоподписанный сертификат добавил бы только предупреждение браузера на каждый
вход. Выпуск Let's Encrypt для такой панели тоже не имеет смысла и `mtproxyl
panel cert` об этом предупредит: до неё не дойти по домену. Если панель позже
понадобится снаружи — поменяйте `listen` в конфиге и перезапустите её.

### Шифрование

Панель принимает пароль администратора и выдаёт токен сессии, поэтому
установщик спрашивает про TLS и по умолчанию предлагает включить его:

| Вариант | Когда подходит |
|---|---|
| Самоподписанный сертификат | по умолчанию: работает сразу, браузер предупредит один раз |
| Let's Encrypt | есть домен с A-записью на этот сервер |
| Свой сертификат | уже есть файлы .crt и .key |
| Без шифрования | только для доступа через localhost или туннель |

Самоподписанный сертификат панель создаёт сама при первом запуске и больше
не трогает: перезапуск его не меняет, так что предупреждение браузера
появится один раз. Без TLS cookie сессии не получает флаг `Secure` — об этом
панель пишет в журнал при старте.

Let's Encrypt на домене, для которого сертификат уже выпущен — обычно это
Selfmask на том же сервере, — панель не выпускает второй, а берёт готовый:
свой ACME ей тогда не нужен, порт 80 остаётся за nginx заглушки, продление
делает certbot. Тот же обмен работает и в обратную сторону: Selfmask,
настроенный после панели, передаёт ей свой сертификат сам.

Если готового сертификата нет, а порт 80 занят, выпуск берёт на себя MTProxyL:
собственному ACME панели порт нужен и при старте, и при каждом продлении, а он
умеет либо отдать проверку домена заглушке Selfmask, либо освободить порт на
несколько секунд. Установщик предупредит об этом и предложит выпуск сразу
после установки; повторить можно командой `mtproxyl panel cert <домен>` или
пунктом «Выпустить сертификат» в меню панели MTProxyL.

### Управление

Через MTProxyL:

```bash
mtproxyl panel status      # состояние
mtproxyl panel restart     # перезапуск
mtproxyl panel uninstall   # удаление (спросит, оставить ли конфиг и данные)
```

Напрямую — панель ставится и без MTProxyL, поэтому и обычные операции с ней
не обязаны идти через его CLI:

```bash
sudo systemctl status mtproxyl-panel
sudo systemctl restart mtproxyl-panel
journalctl -u mtproxyl-panel -f
```

При удалении самого MTProxyL (`mtproxyl uninstall`) панель не удаляется
молча — установщик спросит про неё отдельно. Если её оставить, интеграция
отключается: снимаются права sudo на исчезающий скрипт MTProxyL и
выставляется `enabled = false`, после чего панель работает как обычная
панель telemt.

### Удаление без MTProxyL

Тем же `install.sh`, что и для установки — двумя эквивалентными способами:

```bash
# Уже скачан как install-panel.sh (см. "Отдельно" выше):
sudo sh install-panel.sh uninstall
sudo sh install-panel.sh purge

# Без сохранения на диск — сразу из пайпа:
curl -fsSL https://raw.githubusercontent.com/Liafanx/MTProxyL/main/mtproxyl-panel/install.sh | sudo sh -s -- uninstall
curl -fsSL https://raw.githubusercontent.com/Liafanx/MTProxyL/main/mtproxyl-panel/install.sh | sudo sh -s -- purge
```

`-s --` в пайпе обязателен именно в таком виде: без `-s` sh попытается
открыть `uninstall`/`purge` как путь к файлу скрипта, а не передаст их
установщику аргументом.

| | `uninstall` | `purge` |
|---|---|---|
| Служба и бинарник | удаляются | удаляются |
| Права sudo (`/etc/sudoers.d/mtproxyl-panel*`) | удаляются | удаляются |
| Конфиг (`/etc/mtproxyl-panel`) | остаётся | удаляется |
| Данные (`/var/lib/mtproxyl-panel`) | остаются | удаляются |
| Системный пользователь `mtproxyl-panel` | остаётся | удаляется |

Конфиг хранит логин и хеш пароля администратора — после `uninstall`
повторная установка находит его и пропускает мастер настройки, пароль
остаётся прежним. `purge` не оставляет ничего.

### Известные проблемы

**Ubuntu 26+: установка падает на `visudo: invalid sudoers file`.**

```
sudoers:15:37: syntax error: wildcards are not allowed in command arguments
mtproxyl-panel ALL=(root) NOPASSWD: /usr/bin/journalctl -u telemt -n * --no-pager -o short-iso
```

По умолчанию там `sudo` — это sudo-rs (переписанная на Rust реализация), и её
`visudo` пока не умеет символ `*` в аргументах команд — а часть правил
sudoers панели на нём держится (например, чтение диапазона строк лога).
Установщик покажет эту же подсказку прямо в момент ошибки. Лечится
переключением на классический sudo:

```bash
sudo update-alternatives --set sudo /usr/bin/sudo.ws
```

После этого установку можно повторить.

## Что умеет

### От telemt

| Раздел | Возможности |
|---|---|
| Дашборд | здоровье, аптайм, соединения, трафик, ошибки по классам, сводка доступности из РФ; запуск, перезапуск и остановка движка при включённом мосте |
| Доступность из России | проверка прокси снаружи зондами Globalping, автопроверка по расписанию, свой адрес проверки, телеграм-бот с алертами о падении и о потере связи с дата-центрами |
| Пользователи | создание, редактирование, удаление, квоты, ссылки `tg://`, накопленный трафик, история IP с GeoIP |

> **В режиме Manager пользователей ведёт MTProxyL, а не движок.** Его конфиг
> примонтирован в контейнер только для чтения, поэтому telemt не может
> записать пользователя и отвечает «Device or resource busy». Панель создаёт,
> правит и удаляет их через `mtproxyl secret`, а статистику по-прежнему берёт
> из API движка. Секрет при правке можно только перевыпустить — задать
> произвольный MTProxyL не умеет.
>
> По той же причине из панели нельзя сохранить конфиг движка: страница
> «Конфигурация» в этом режиме доступна только для просмотра. Порт, домен и
> маскировка меняются в «Настройках прокси», остальное — в «Экспертных
> параметрах» или в «Супер эксперте».
| Телеметрия | 11 разделов: гейты, пул ME, качество апстримов, NAT/STUN, самопроверка и др. |
| Безопасность | режим только чтения, белый список, заголовок авторизации, действующие лимиты |
| Конфигурация | форма быстрых настроек и полноценный редактор TOML |
| Логи | потоковый просмотр с фильтром и скачиванием |
| Обновление | обновление панели с проверкой контрольной суммы и откатом; при включённом мосте — и обновление самого MTProxyL |

> **Накопленный трафик и история IP приходят не от движка.** Его списки
> «активные»/«недавние» живут только текущую сессию и пустеют при перезапуске
> цели или простое пользователя. MTProxyL копит и то и другое на диске и отдаёт
> по тому же имени пользователя, поэтому в карточке видно и сессионное
> состояние, и накопленное за всё время — в обоих режимах.
>
> Пополняет историю systemd-таймер MTProxyL, а не открытая панель: раньше
> адреса записывались только в момент запроса списка пользователей, то есть
> пока браузер открыт. Частота снимков — «Обслуживание» → интервал истории IP.
>
> Страна, город и провайдер появляются, только если установлена база GeoIP:
> раздел «Дополнения» или `mtproxyl geoip install`. Панель также подхватит
> базу, установленную системным пакетом, и заметит её без перезапуска.

> **«Доступность из России» отвечает на вопрос, который сервер о себе задать
> не может.** Прокси может быть полностью здоров на сервере и при этом мёртв
> для пользователей: адрес закрыт национальным фильтром, а порт для всех
> остальных открыт. Панель просит публичную сеть зондов Globalping выполнить
> HTTPS-рукопожатие с портом прокси — именно с российских резидентских
> (eyeball) сетей, потому что фильтрация применяется к абонентскому трафику, а
> зонд в дата-центре спокойно видит сервер, до которого не достучаться из дома.
>
> Успехом считается полученный TLS-сертификат: это то же рукопожатие, что
> делает клиент Telegram, поэтому — в отличие от простого TCP-коннекта —
> заметен и случай, когда порт отвечает, но сессия рвётся на рукопожатии.
> Прав root не нужно и на сервер ничего не ставится: это обычные исходящие
> запросы к API.
>
> Проверка по расписанию выключается переключателем на странице — состояние
> видно и на дашборде. Она тратит квоту и обращается к прокси, а нужна не всем;
> кнопка «Проверить сейчас» работает независимо от него. По умолчанию включена.
>
> Что проверять, панель определяет сама (домен заглушки Selfmask, привязанный
> адрес, иначе внешний IP; порт и fake SNI — у текущего режима). Форма **«Что
> проверять»** позволяет задать адрес, порт и SNI руками: автоопределение
> слепо там, где адрес знает только оператор — прокси за CDN, второй домен на
> том же сервере, проброшенный порт. Пустое поле означает «определить самому»,
> и в подсказке стоит то, что подставится.

> **Телеграм-бот отвечает на вопрос «а кто это увидит».** Вердикт проверки до
> сих пор видел только тот, у кого открыта вкладка панели, — а падение
> доступности до 50–60% обычно значит, что адрес попал под фильтр у части
> операторов, и знать об этом хочется в момент события.
>
> Раздел **«Телеграм-бот»** на той же странице просит три вещи: токен от
> [@BotFather](https://t.me/BotFather), ID админа и порог алерта (по умолчанию
> 60%). ID бот пришлёт сам — сохраните токен, включите бота и напишите ему
> `/start`. Этот шаг обязателен в любом случае: Telegram не даёт боту написать
> первым, пока человек не открыл диалог.
>
> В чате бот держит **ровно одно сообщение** и переписывает его после каждой
> проверки — и плановой, и по кнопке. Бегать по истории в поисках свежих цифр
> не приходится. Но правка сообщения в Telegram беззвучна, поэтому на событии
> — уходе ниже порога, напоминании раз в 30 минут и возврате выше — сообщение
> отправляется заново со звуком, а прежнее убирается. Своё сообщение старше 48
> часов Telegram удалять не даёт: такое ужимается в одну строку со ссылкой
> вниз, чтобы рядом не висел второй «статус» со старыми цифрами.
>
> Под сообщением две кнопки. **«Проверить сейчас»** запускает настоящее
> измерение — то же самое, что кнопка на странице, с её минутным кулдауном и
> расходом квоты; отказ объясняется всплывашкой прямо на кнопке.
> **«Обновить»** просто перечитывает последний вердикт и квоту не тратит.
>
> Кроме процента и списка всех зондов в сообщении есть A-запись домена цели и
> внешний адрес самого сервера. Их расхождение — частая причина «прокси здоров,
> а не работает»: переехали на новый VPS и забыли поправить DNS.
>
> Сорвавшаяся проверка нулевой доступностью не считается: измерения не было,
> значит и вывода о прокси нет. Бот покажет причину рядом с последним
> известным вердиктом и промолчит про бан — ложный алерт приучает не верить
> алертам.
>
> Токен и ID хранятся в `<data_dir>/telegram-bot.json` с правами 600 и наружу
> не отдаются: в панель возвращается только признак, что токен задан. Там же
> лежит id сообщения, поэтому перезапуск панели не плодит в чате новые.
>
> Время бот показывает в часовом поясе сервера и подписывает его смещением от
> UTC. Подпись нужна, потому что панель форматирует время в браузере читателя,
> а бот — на сервере: без неё расхождение выглядит поломкой. Смену пояса на
> сервере бот подхватывает сам, перезапуск панели для этого не нужен.

> **Связь с дата-центрами — вторая половина картины, и без неё первая врёт.**
> Проверка зондами отвечает на вопрос «видят ли меня клиенты» — это вход. Но
> фильтрация у российского хостера часто режет не вход, а выход: виртуалка
> снаружи доступна, зонды показывают прежние 95%, а прокси при этом не может
> писать в дата-центры Telegram, и клиенты не работают.
>
> Поэтому бот вторым блоком показывает исходящую связь: сколько живых
> писателей при скольких нужных, долю неудачных подключений за интервал и
> задержку до каждого дата-центра. Данные берутся у самого движка раз в минуту
> — они локальные и квоты не тратят, поэтому обрыв замечается за минуту, а не
> за пятнадцать, как бан входа.
>
> Тревога поднимается по трём условиям: писателей не осталось вовсе, живых
> устойчиво меньше, чем нужно, или доля неудачных подключений держится выше
> порога (по умолчанию 20%, настраивается там же в форме). Слово «устойчиво»
> здесь существенно: `required_writers` — величина не постоянная, движок сам
> поднимает цель под нагрузку, и живые писатели догоняют её не мгновенно.
> Первый же боевой прогон на нагруженном прокси показал, что без этого условия
> каждое расширение пула приходит тревогой «связь потеряна», а через минуту
> «восстановлена». Поэтому всё, кроме полного отсутствия писателей, должно
> продержаться три опроса подряд. **По отдельным дата-центрам
> тревоги нет намеренно**: на работающем сервере покрытие по ним штатно скачет
> от 0 до 100, а у медиа-дата-центров писателей часто нет вовсе. Тревога по
> ним звучала бы круглосуточно, и её перестали бы замечать вместе с
> настоящими. Цифры по дата-центрам показываются, решение принимается по сумме.
>
> Там же ловятся ещё два события: движок упал, ушёл в режим только чтения или
> перезапустился — и сменился внешний адрес сервера (это значит, что DNS и
> выданные клиентам ссылки протухли). Если middle proxy не используется, блока
> просто нет: это не авария, а «судить не о чем».

> **Команды и пауза.** Бот регистрирует команды в Telegram, поэтому работают
> подсказки при наборе `/`, и дублирует их кнопками под полем ввода:
> `/status` — показать статус сейчас, `/check` — запустить проверку,
> `/mute` и `/unmute` — заглушить тревоги на время работ, `/help` — что
> означают цифры. `/status` и `/check` переотправляют сообщение вниз чата без
> звука, чтобы не искать его в истории.
>
> Пауза глушит только звук: инциденты продолжают считаться, статус тихо
> обновляется, а в шапке висит строка о том, до какого времени сирена
> выключена. Снятие паузы при живой аварии сообщает об этом отдельно — иначе
> легко снять паузу и решить, что всё наладилось.

### От MTProxyL

Появляются только при включённой интеграции.

| Раздел | Возможности |

## Как устроена интеграция

Движок telemt отдаёт REST API — оттуда берутся пользователи, статистика и
конфиг. Но переключение режимов, Selfmask и правила фаервола живут на уровне
хоста, и API их не покрывает. Для них панель вызывает CLI MTProxyL
(`internal/mtproxylctl`) и разбирает его вывод.

Панель работает под своим непривилегированным пользователем
`mtproxyl-panel`. Команды MTProxyL требуют root, поэтому установщик создаёт
`/etc/sudoers.d/mtproxyl-panel-mtproxyl` — **список конкретных разрешённых
команд**, а не право запускать `mtproxyl` целиком. Файл удаляется при
отключении интеграции и при удалении панели.

Обратная сторона именного списка: команду, появившуюся в новой версии, sudo
не пропустит, пока файл не перепишут, — а обновление панели её же кнопкой
меняет только бинарник. Панель на такой отказ отвечает прямо: «не хватает прав
sudo, обновите их: `mtproxyl panel install`».

Значения, приходящие из браузера, проверяются дважды: панелью перед вызовом и
самим MTProxyL по его каталогу параметров.

### Параметры и применение — два разных шага

MTProxyL разделяет сохранение параметров и применение, панель это повторяет.
На страницах лимитера и Selfmask есть обе кнопки: **«Сохранить и применить»**
делает оба шага сразу, **«Только сохранить»** — откладывает применение.

Интерактивные мастера MTProxyL панель не запускает: под обходом подтверждений
они взяли бы свои значения по умолчанию и проигнорировали выбранное в
интерфейсе. Вместо них используются неинтерактивные команды — `nft set` +
`nft apply`, `selfmask set` + `selfmask apply`.

## Конфигурация

`/etc/mtproxyl-panel/config.toml`. Полный пример с комментариями —
[`config.example.toml`](config.example.toml).

Секция интеграции:

```toml
[mtproxyl]
enabled = true
script_path = "/opt/mtproxyl/mtproxyl.sh"
install_dir = "/opt/mtproxyl"
use_sudo = true
# command_timeout = "10m"
```

При `enabled = false` разделы MTProxyL скрываются, и панель работает как
обычная панель для telemt.

Проверка доступности (работает и без интеграции):

```toml
[globalping]
# enabled = true          # секции нет — считается включённой
# check_interval = "15m"  # 20 зондов раз в 15 минут — 80 кредитов в час
# probe_limit = 20        # максимум 50
# api_token = "gp_…"      # проще задать в панели, на самой странице
# override_host = "my-proxy.example.com"
```

Globalping отпускает 250 кредитов в час (500 с токеном), один зонд — один
кредит. Панель считает потраченное скользящим часом и показывает остаток, но
решение о лимите за сервисом: проверка уходит всегда, а если кредитов не
осталось, он отвечает отказом. Такой отказ не затирает прошлый вердикт —
измерения не было. Токен удобнее задать прямо на странице «Доступность из
России»: это поле переопределяет `api_token` из конфига и применяется без
перезапуска. `override_host` задаёт адрес при старте, а форма «Что проверять» в
панели важнее его и умеет ещё порт и SNI; выбор хранится в
`<data_dir>/availability-target.json`.

## Ограничения

- **Обновление telemt из панели недоступно при включённой интеграции.**
  Встроенный механизм рассчитан на telemt как systemd-сервис, а в режиме
  Manager MTProxyL держит движок в Docker. Обновляйте через `mtproxyl engine`.
- **Мастер Selfmask из панели не запускается.** Панель задаёт параметры
  (домен, тип сертификата, шаблон) и применяет их командой `selfmask apply`;
  интерактивный мастер `selfmask setup` остаётся только в CLI.
- **Одна операция за раз.** Переключение режима, установка Selfmask,
  восстановление бэкапа и применение правил не запускаются параллельно —
  они пишут в одни и те же файлы настроек.
- **Один администратор.** Ролей и двухфакторной аутентификации нет. Учитывайте,
  что переключение режима — root-действие на хосте, доступное владельцу сессии.
- **Только в режиме Manager** доступны бэкапы, маршруты, экспертные параметры и
  супер эксперт: все они опираются на владение конфигом движка, которого в
  режиме Reanimator нет. В интерфейсе они скрыты.
- **censorcheck не перенесён.** Проверка ограничений сервера запускает сторонний
  скрипт, скачанный из сети; такое по нажатию кнопки в вебе делать не стоит —
  команда осталась в меню MTProxyL.

## Сборка из исходников

```bash
cd mtproxyl-panel
make            # фронтенд + бинарник
make release    # сборки под x86_64 и aarch64 с контрольными суммами
```

Нужны Go 1.25+ и Node.js 20+.

Разработка:

```bash
make dev-frontend   # Vite с горячей перезагрузкой
make dev-backend    # go run с локальным config.toml
make hash-password  # хеш пароля для config.toml
```

Проверки, которые гоняет CI:

```bash
gofmt -l . && go vet ./... && go test ./...
cd frontend && npx tsc --noEmit
```
